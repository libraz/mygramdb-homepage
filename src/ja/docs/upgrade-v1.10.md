# v1.10.2 へのアップグレード

::: info 現行リリースへ更新する場合
現行パッチの確認事項、ソースの必須メタデータ設定、ネイティブクライアントの再ビルドを含む、[v1.11 のアップグレード手順](/ja/docs/upgrade-v1.11)も実施してください。
:::

v1.10.1 と v1.10.2 のパッチリリースでは、レプリケーションの安全性、設定検証、ダンプ復旧、API 認証、プロトコル間で共有するレート制限を修正しています。実行中のノードを置き換える前に、次の項目を確認してください。

## 更新前の確認

### 管理トークンを設定する

TCP または HTTP リスナーをループバック以外へ公開する前に `api.admin_token` を設定します。TCP を Unix socket なしで非ループバックアドレスにバインドする場合、または HTTP を有効にして非ループバックアドレスにバインドする場合はトークンが必須です。Unix socket で除外されるのは TCP リスナーだけです。

本番環境では `MYGRAM_API_ADMIN_TOKEN` を優先してください。設定に `api` ブロックがなくても、この環境変数は適用されます。十分な長さの値を生成し、設定ファイルやシェル履歴に残さないように管理します。

```bash
openssl rand -hex 32
```

TCP クライアントは、管理コマンドより前に同じ接続で `AUTH <token>` を送信します。HTTP の管理リクエストでは `Authorization: Bearer <token>` を使います。TCP はトークンを暗号化しないため、信頼できるネットワークか暗号化した経路で使ってください。リクエストの形式は、[プロトコルリファレンス](/ja/docs/protocol) と [HTTP API ガイド](/ja/docs/http-api) を参照してください。

### ネットワークと接続先の設定を検証する

設定パーサーは、ネットワークの境界を弱める次の組み合わせを拒否します。

- 公開 TCP リスナーまたは有効な HTTP リスナーに `api.admin_token` がない
- 非ループバックリスナーと `0.0.0.0/0` または `::/0` の公開許可リスト
- `cors_allow_origin` を指定していない CORS の有効化
- サーバー証明書の検証を有効にしたまま CA を指定していない MySQL TLS
- GTID を使えない MySQL ソース、または `mysql.user` が未設定のソース

展開前に本番環境で使うファイルを検証します。

```bash
mygramdb -t /etc/mygramdb/config.yaml
```

MygramDB は MySQL 8.4/9.x と MariaDB 10.11+/11.x/12.x に対応します。GTID レプリケーションを使い、`binlog_format=ROW` と `binlog_row_image=FULL` を設定してください。

### 起動を拒否する設定を確認する

再起動前に次の設定を更新します。

- `dump.load_on_startup: true` には `replication.start_from: "snapshot"` が必要です。`latest` と `gtid=...` は、ダンプの GTID から設定済みの位置までの binlog 変更を飛ばす可能性があるため拒否されます。
- `cache.ttl_seconds`、`cache.eviction_batch_size`、`cache.invalidation.batch_size`、`cache.invalidation.max_delay_ms` は `2147483647` 以下にします。
- 型が `datetime`、`date`、`timestamp` の `required_filters` の値には、末尾の `Z`、数値オフセット、その他の接尾辞を付けません。エポック秒または `mysql.datetime_timezone` で指定したオフセットの ISO 日時を使います。
- 型が `time` の `required_filters` の値は `-838:59:59` から `838:59:59` の範囲に収めます。
- `float` はフィルタ型として使えません。`FLOAT` カラムを主キー、テキストソース、フィルタに指定すると、レプリケーション開始時に拒否されます。
- `OPTIMIZE` はインデックスのメモリ使用量の約 2.1 倍の空きメモリを必要とし、空きが不足すると開始を拒否します。

### 環境変数の上書きを確認する

起動時の設定処理は、`mysql` ブロックがなくても `MYGRAM_MYSQL_HOST`、`MYGRAM_MYSQL_PORT`、`MYGRAM_MYSQL_USER`、`MYGRAM_MYSQL_PASSWORD`、`MYGRAM_MYSQL_DATABASE` を適用します。`MYGRAM_MYSQL_PORT` は `1` から `65535` までの整数でなければなりません。`MYGRAM_API_ADMIN_TOKEN` も `api` ブロックなしで適用されます。空の環境変数は未設定として扱い、設定ファイルまたは組み込みデフォルトへフォールバックします。

### Docker デプロイを更新する

同梱の Compose スタックは、TCP と HTTP のポートを `127.0.0.1` に公開します。別ホストからコンテナへ接続する場合は、ホスト側のポートマッピングを明示的に変更します。

現在の[環境変数テンプレート](https://github.com/libraz/mygram-db/blob/main/.env.example)から `.env` を作り直し、次の値を確認してください。

- `API_ADMIN_TOKEN` は必須で、プレースホルダー値は拒否されます。
- `MYSQL_PASSWORD` と `MYSQL_ROOT_PASSWORD` にテンプレートのプレースホルダーを残しません。
- コンテナ内のリスナーは `API_CONTAINER_BIND` と `API_HTTP_CONTAINER_BIND` で設定します。Compose はその用途に `API_BIND` と `API_HTTP_BIND` を使いません。
- `NETWORK_ALLOW_CIDRS` には、ホスト側のクライアントが使ったアドレスだけでなく、MygramDB から見える Docker ブリッジのアドレスを含めます。

リモートアクセスが必要な場合だけ、ホスト側のポートをループバック以外に公開してください。現行の一式は [Docker デプロイガイド](/ja/docs/docker-deployment)を参照してください。

### 実行中の MySQL 接続先変更をやめる

`mysql.host` と `mysql.port` は起動時にだけ読み込みます。`SET mysql.host=...` と `SET mysql.port=...` は immutable-variable エラーを返します。接続先を変えるときは、設定ファイルを修正して MygramDB を再起動してください。

自動再接続は設定済みの接続先を使い続け、ソースサーバー UUID が変わっていると拒否します。実行中のプロセスを `SET` で別の接続先へ向けるフェイルオーバー自動化は削除してください。

### 共有レート制限を見直す

TCP と HTTP はクライアントアドレスごとに 1 つのトークンバケットを使います。両方のプロトコルを使うクライアントにも、プロトコルごとのバースト量は与えられません。以前の合計レートを維持する場合は、`api.rate_limiting.capacity` と `api.rate_limiting.refill_rate` を増やしてください。実行時の `SET api.rate_limiting.*` は共有リミッターを更新します。

### クエリキャッシュの状態を確認する

キャッシュキーの直列化プレフィックスが変わりました。更新後のクエリキャッシュは空の状態から始まるため、エントリが再び温まるまでキャッシュミスが増えます。

### レプリケーションの停止条件を確認する

適用できず、無害にスキップできるとも証明できない binlog イベントがあると、レプリケーションは停止します。対象は、トランザクション圧縮、`gtid_mode` が `ON` でない場合の匿名トランザクション、レプリケーション対象テーブルへの `LOAD DATA INFILE`、部分 JSON 行イメージ、未対応の MariaDB 圧縮 binlog イベント、ソースが宣言した binlog の欠落です。このイベント単位のルールは、v1.10.2 でデコードする MariaDB の `COMPRESSED` カラムのペイロードとは別です。更新前にこのようなイベントの影響を受けていた場合は、ソース設定を修正した後、すべてのレプリケーション対象テーブルに `SYNC` を実行してください。設定だけを直しても、すでにずれたインデックスは修復されません。

## ダンプと起動時復旧

### 既存ダンプの互換性

以前の v1.10.0 の案内では、ソース UUID がない古いダンプを使用できないとしていました。この扱いは v1.10.1 で修正されています。v1.5.4 以降で作成したダンプは復元できます。古いライターが v1.5.3 まで出力していた `header_size` のゼロも読み取ります。v1.3.2 以前で作成したダンプは、投稿リストのバイト順を判別できないため引き続き読み取れません。ソース UUID を記録していないダンプはソース不明として扱い、記録された UUID が実行中のソースと異なる場合は拒否します。

ダンプの互換性検査では、修飾されたテーブル識別子 `<database>.<table>` を使います。複数の DB に同じテーブル名がある場合は、更新後に実際のインデックスを確認してください。古い復元で別のテーブルが選ばれていた場合は `SYNC` で再構築します。

### 起動時のダンプ読み込み

`dump.load_on_startup` は、MySQL の初期スナップショットより前に `dump.dir/default_filename` を読み込みます。ダンプのホスト、ポート、データベース、ソース UUID、GTID、テーブル設定を設定済みのソースと照合します。読み込み、整合性、識別情報の検証に失敗した場合はフォールバックをログに記録し、MySQL のスナップショットから起動します。この設定を有効にするときは `replication.start_from: "snapshot"` を指定してください。

`DUMP SAVE --with-stats` は使えません。`DUMP SAVE [path]` は引き続き使えますが、`DUMP SAVE .` は拒否されます。現行の書き出し処理は、主キー、フィルタ値、テキストが大きすぎるドキュメントを拒否します。`DUMP STATUS` が `COMPLETED` を示したダンプは復元上限を超えません。直後に返る `OK DUMP_STARTED` は保存開始だけを示します。v1.10.1 で作成したダンプはそのまま読み込めます。

更新と同期が終わったら、新しいダンプを作成・検証してからダンプ復旧に使ってください。復元時の上限と運用手順は、[スナップショットコマンド](/ja/docs/snapshot)を参照してください。

## レプリケーション復旧

解析できない binlog イベントがあると、エラーコード `2017` でレプリケーションが停止します。このビルドでサイズを判定できない `TABLE_MAP` のカラム型は、未設定テーブルでも停止の原因になります。テーブルを無視する前に行幅をデコードする必要があるためです。同じイベントは最後に適用したGTID位置に残るため、再接続だけでは先へ進めません。監視対象テーブルのオプションメタデータが欠落または不正な場合も `2017` で停止します。復旧前にソースを `binlog_row_metadata=FULL` に設定してください。優先度の高いテーブルから `SYNC` を実行し、その後、他のすべてのレプリケーション対象テーブルにも1つずつ実行してください。詳しくは[SYNCの復旧手順](/ja/docs/sync-command#%E3%82%A8%E3%83%A9%E3%83%BC-2017-%E3%83%86%E3%82%99%E3%82%B3%E3%83%BC%E3%83%88%E3%82%99%E3%81%A6%E3%82%99%E3%81%8D%E3%81%AA%E3%81%84-binlog-%E3%82%A4%E3%83%98%E3%82%99%E3%83%B3%E3%83%88)を参照してください。

`ALTER TABLE ... RENAME TO ...` でテーブルを設定済みの名前へ変更すると、名前変更の診断を出してレプリケーションを停止します。スキーマ変更を解決し、通常の書き込みを再開する前に対象テーブルを再構築してください。

## 更新チェックリスト

1. 十分な長さの管理トークンを設定し、すべての管理クライアントを更新する。
2. `mygramdb -t` で本番設定を検証する。
3. 対応する MySQL/MariaDB のバージョン、GTID、`ROW` 形式の binlog、`FULL` 行イメージを確認する。
4. 時間型の required filter、拒否される `FLOAT` の用途、ダンプ起動設定、キャッシュ上限を確認する。
5. 環境変数の上書きを適用し、root パスワードを含む Docker ファイルを作り直す。
6. 実行中の MySQL 接続先変更と `DUMP SAVE --with-stats` の呼び出しを削除する。
7. 古いダンプのテーブル識別子を確認し、現在のダンプを検証して、ロールバック用のコピーを残す。
8. TCP と HTTP で共有するレートの上限を計算し直す。
9. 再起動後に ready になるまで待ち、検索と管理操作のスモークテストを実行し、レプリケーション遅延が更新されることを確認する。

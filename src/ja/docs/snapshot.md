# スナップショットとダンプ復旧

## ダンプに含まれるもの

ダンプは、MygramDB が索引化したデータ、設定の互換性メタデータ、レプリケーション位置をバイナリで保存した復旧用ファイルです。MySQL 自体のバックアップではありません。MySQL のバックアップと binlog は別に保持してください。

`DUMP SAVE` は常に現行のダンプ形式で書き出します。読み込み側は形式 1 と形式 2 を受け付けます。互換性メタデータの版が 1 のダンプも読み込めます。現行のメタデータには MySQL のソースサーバー UUID も記録されます。未対応の新しい形式は拒否されます。

対応している古い形式のダンプは引き続き復元できます。旧形式の `header_size=0` も認識します。ソース UUID を記録していないダンプはソース不明として受け付けますが、記録された UUID が実行中のソースと異なる場合は拒否します。投稿リストのバイト順が判別できない旧形式のダンプは読み込めません。

## ダンプを保存する

```mygram
DUMP SAVE
DUMP SAVE /var/lib/mygramdb/dumps/before-maintenance.dmp
```

`DUMP SAVE` に `--with-stats` オプションはありません。このフラグを含むコマンドは無効です。

`DUMP SAVE` はバックグラウンド処理を開始し、すぐに `OK DUMP_STARTED <filepath>` を返します。これは保存完了を意味しません。`DUMP STATUS` が `COMPLETED` を示すまで確認し、`result_filepath` を確認してから `DUMP VERIFY` で検証してください。`FAILED` の場合は `error` を調べ、そのファイルを復旧に使わないでください。

設定済みの全テーブルで初期ロードが完了するまでは、`DUMP SAVE` は `ERROR 6029` を返します。管理トークンを設定していない場合は、`mygram-cli --wait-ready DUMP SAVE <path>` を使うとサーバーのロード中や未準備の応答を再試行できます。`api.admin_token` を設定している場合は、まず `mygram-cli --wait-ready INFO` で準備完了を待ってから、認証済みの同じ接続で `AUTH` と `DUMP SAVE <path>` を送ってください。既定の再試行回数は100回です。`--retry N` で有限の回数を変更でき、使い切っても準備が完了しない場合は非ゼロで終了します。

保存時は一貫した GTID を記録するために動作中のレプリケーションリーダーを停止してドレインし、終了後に再開します。操作前から手動停止中だったリーダーは停止したままです。レプリケーションが有効な場合は現在の GTID が必要です。ファイルを書き出す前に、`DUMP SAVE` は復元時の上限を現在のデータへ適用し、主キー、フィルタ値、テキストフィールドが大きすぎる場合や `dump.restore_memory_budget_mb` を超えるデータになる場合は拒否します。そのため、`DUMP STATUS` が `COMPLETED` を示したダンプが復元時に厳しいメモリ検査で拒否されることはありません。`DUMP SAVE .` は `.` がダンプディレクトリ自体を指し、その配下のファイルにならないため拒否されます。検索は継続しますが、大きなダンプの保存中は MySQL への追従が遅れることがあります。`SYNC`、`DUMP LOAD`、`OPTIMIZE`、定期スナップショットは同時に実行できません。

制御文字を含むダンプパスは拒否され、`DUMP SAVE` と `DUMP LOAD` の応答にパス中の制御文字は出力されません。書き込みには一時ファイルを使い、rename で確定します。POSIX では atomic rename の前にファイルを fsync します。V2 ではエンコード済みセクションごとに 4 GiB の上限があり、`DUMP SAVE` はこの形式上限を超えるデータを拒否します。

```mygram
DUMP SAVE .
```

このコマンドは拒否されます。`dump.dir` の配下にファイル名を指定してください。

## 復元前に検証して確認する

```mygram
DUMP VERIFY /var/lib/mygramdb/dumps/mygramdb.dmp
DUMP INFO /var/lib/mygramdb/dumps/mygramdb.dmp
```

`DUMP VERIFY` は稼働中のデータを変更せずにファイルとセクションの整合性を検証します。`DUMP INFO` は形式、GTID、テーブル数、フラグ、サイズ、作成時刻を表示します。手動復元の前に対象ファイルを検証してください。ただし、整合性が正しくても、現在の MySQL ソースに対応するファイルとは限りません。

形式 2 のダンプでは、検証時にファイルとセクションの CRC をストリーム処理し、必須の CRC フラグがないヘッダーを拒否します。また、`dump.restore_max_section_mb` を超えるセクションも拒否します。復元では、稼働中のテーブルを置き換える前に、`dump.restore_memory_budget_mb` の範囲でデータをステージングします。既定値は、エンコード済みセクションごとに 2048 MiB、合計ステージングメモリに 4096 MiB です。ホストの容量と信頼できる最大ダンプに合わせて両方を設定してください。上限による拒否は、無制限のメモリ確保からプロセスを守ります。

## 手動で復元する

```mygram
DUMP VERIFY mygramdb.dmp
DUMP INFO mygramdb.dmp
DUMP LOAD mygramdb.dmp
```

`DUMP LOAD` は稼働中のインデックスとドキュメントストアを置き換えます。レプリケーションを停止し、置き換え前にダンプを検証し、読み込んだ GTID を設定して検索統計を再構築し、クエリキャッシュを消去してからレプリケーションを復帰させます。復元が成功すると、復元した全テーブルは初期化済みになります。置き換え後にリーダーを再開できない場合も、MygramDB は復元済みデータを提供し続け、レプリケーションを停止したまま readiness を false にします。

復元テーブルはステージングしてから稼働データへ適用します。検証またはデコードに失敗した場合、現在のインデックスとドキュメントストアは変更されません。

索引対象テーブルの互換性設定が異なるダンプ、設定済みソースと MySQL の host、port、database が異なるダンプ、記録されたソース UUID が実行中のソースと異なるダンプは拒否されます。ソース UUID を記録していないダンプはソース不明として受け付けます。空でないレプリケーション位置を、GTID を持たないダンプで置き換えることもできません。

## 起動時に復元する

`dump.load_on_startup: true` を設定すると、起動時に `dump.dir/default_filename` のファイルだけを復元します。

```yaml
dump:
  dir: /var/lib/mygramdb/dumps
  default_filename: mygramdb.dmp
  load_on_startup: true
  restore_memory_budget_mb: 4096
  restore_max_section_mb: 2048
```

レプリケーションを有効にして `dump.load_on_startup: true` を使う場合、`replication.start_from: snapshot` が必要です。`latest` と `gtid=...` はダンプの GTID を無視するため、設定検証で拒否されます。起動時には設定済み MySQL ソースを確認し、ダンプのテーブル互換性、host、port、database、ソース UUID、GTID を検証します。ソース UUID を記録していない起動時ダンプはソース不明として受け付けますが、記録された UUID が異なる場合は拒否します。レプリケーションを有効にしている場合、起動時ダンプには GTID が必要です。成功するとダンプを復元してテーブルを初期化済みにし、ダンプの GTID からレプリケーションを開始して追従します。

既定ファイルがない、破損している、互換性がない、別のソースから作られた、または検証できない場合、MygramDB は起動時復元の失敗をログに残し、通常の MySQL 初期スナップショットへフォールバックします。この場合はダンプを調査してください。MySQL に全表読み取りの負荷がかかる可能性があります。

起動時のダンプ復元に成功した後で binlog リーダーの開始に失敗した場合、MygramDB は復元済みデータを提供し続け、レプリケーションを停止したまま readiness を false にします。復元済みダンプがない場合の同じ開始失敗は致命的です。

起動時のダンプ復元後にレプリケーションを開始できても、ソースへの追いつきに失敗した場合、MygramDB はリーダーを停止し、復元済みデータを利用可能な状態で保持して `not_ready` になります。起動を中断しないため、トラフィックを流す前にレプリケーションエラーを確認してください。

## 保持と保管

```yaml
dump:
  interval_sec: 600
  retain: 3
```

`dump.retain` は 1～100 ファイルを受け付け、既定値は 3 です。定期ダンプには時刻付きの `auto_*.dmp` という名前が付き、保持数を超えた古い自動ファイルだけが削除されます。定期スナップショットは、設定されたすべてのテーブルの初期ロードが完了するまで待機します。手動の `DUMP SAVE` ファイルは保持処理で削除されません。ダンプには索引化した内容と接続メタデータが含まれるため、アクセスを制限し、保護されたストレージに置き、隔離環境で復元を試してください。

## トラブルシューティング

| 状況 | 対処 |
| --- | --- |
| CRC 不一致または切り詰めエラー | 読み込まないでください。別の検証済みコピーを使い、保存先や転送経路を調べます。 |
| 未対応の形式 | その形式を読める MygramDB を使うか、互換性のあるダンプを選びます。 |
| ソースまたは UUID が不一致 | 強制しないでください。設定済みソースのダンプを使うか、復旧前に意図的に設定を変更して再起動します。 |
| 復元上限を超えた | ファイルを検証し、十分なメモリを用意してから設定上限を上げます。 |
| 復元成功後も readiness が false | `/health/ready` または `INFO` のレプリケーションエラーを確認します。データは入っていますが、レプリケーションの修復が必要です。 |

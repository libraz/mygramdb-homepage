# 仕組み

MygramDB は N-gram インデックスを中心に構築されたインメモリ全文検索エンジンです。このページでは、テキストのインデックス方法、検索の実行過程、キャッシュの整合性維持について解説します。

::: info 初めて読む場合
このページでは内部構造を説明します。まずは「文字列を N-gram に分ける」「N-gram から候補ドキュメントを探す」「必要なら保存済みの正規化テキストで確認する」という 3段階だけ押さえれば十分です。
:::

## N-gram インデックス

MygramDB はテキストを、重なり合う文字列の断片である N-gram に分割します。デフォルトでは、ASCII テキストにも CJK の漢字にも**バイグラム**（2文字）を使います。CJK の漢字だけ別の長さにするには `kanji_ngram_size` を設定します。

::: info 用語補足
**トークン化**は、検索しやすいようにテキストを小さな単位へ分ける処理です。MygramDB は辞書を使わず、文字の並びそのものを N-gram として扱うため、言語を問わず同じ方法で動作します。
:::

たとえば `search` は、次のバイグラムに分割されます。

```
"search" → ["se", "ea", "ar", "rc", "ch"]
```

`東京都` のような日本語の文字列も、デフォルト設定ではバイグラムになります。

```
"東京都" → ["東京", "京都"]
```

各 N-gram は**ポスティングリスト**（その N-gram を含むドキュメント ID のソート済みリスト）に対応します。ドキュメントを挿入すると、テキストがトークン化され、各 N-gram のポスティングリストにドキュメント ID が追加されます。

<DocDiagram name="ngram-index" alt="「search」がバイグラム se・ea・ar・rc・ch に分割され、それぞれが DocID 昇順のポスティングリストに対応し、ドキュメント 1 と 42 がすべてのリストに現れて積集合に残ることを示す図" />

ドキュメント ID（DocID）は `uint32_t` 型で、テーブルあたり最大 40億件のドキュメントに対応します。

## ポスティングリスト圧縮

N-gram の出現頻度は均一ではありません。MygramDB はポスティングリストをデルタエンコーディングまたは Roaring ビットマップで保持します。`OPTIMIZE` は密度に応じて形式を選びます。ドキュメントの追加時にも、件数に応じた自動変換があります。

| 戦略 | 使用条件 | 表現方法 |
|------|---------|---------|
| **デルタエンコーディング** | 疎なリスト（`OPTIMIZE` 後の密度が通常 18%未満） | ソート済み ID を固定幅の差分で格納 |
| **Roaring ビットマップ** | 密なリスト（`OPTIMIZE` 後の密度が通常 18%以上）、または 4,096件を超えるリスト | CRoaring ライブラリによる圧縮ビットマップ |

**密度**は、`（その N-gram を含むドキュメント数）/（テーブル内の全ドキュメント数）` で求めます。

`OPTIMIZE` は、デフォルトで 18% の密度閾値と **0.5倍のヒステリシス**を使います。挿入によってデルタエンコーディングのリストが 4,096件を超えたときは、密度に関係なく Roaring へ自動変換します。Roaring からデルタエンコーディングへ戻るのは、件数が 4,096件以下で、かつ密度が閾値の半分（デフォルト 9%）未満の場合だけです。

::: info 用語補足
**ヒステリシス**は、切り替える条件と戻す条件をずらして、状態が頻繁に行き来しないようにする考え方です。`OPTIMIZE` では 18% で Roaring へ切り替え、9% 未満で戻します。密度が境界付近にあっても、形式が何度も変わりません。
:::

デルタエンコーディングは、出現頻度の低い語を小さく保存できます。`[100, 105, 200]` は `[100, 5, 95]` として格納されます。Roaring ビットマップは頻出語に向いており、検索時に SIMD で高速化した集合演算（積集合、和集合）が使えます。

## 検索パイプライン

検索クエリは、次の段階を順に通過します。

<DocDiagram name="search-pipeline" alt="クエリ受信、解析、N-gram 生成、ポスティングリストの積集合、NOT 除外、カラムフィルタ、verify_text ポストフィルタ、ソート、OFFSET と LIMIT、DocID 返却という10段階のパイプライン図" />

**各ステップの詳細**

1. **クエリ解析** -- 検索語、NOT 語、フィルタ条件、ソート順、ページネーションをクエリから抽出します。

2. **N-gram 生成** -- 各検索語は Unicode 正規化（ICU による NFKC）をしてから N-gram に分割します。語は推定結果サイズの昇順（最小のポスティングリストが先）に並べ、中間結果を小さく保ちます。

3. **ポスティングリストの積集合** -- まず語ごとに、その語の N-gram ポスティングリストすべての積集合を取ります（AND の意味論）。次に、語ごとの結果同士の積集合を取ります。最小の集合から始めると、以降の積集合が安くなります。

4. **NOT フィルタ** -- NOT 語にマッチするドキュメントを候補セットから除外します。

5. **カラムフィルタ** -- フィルタ条件（例: `category = 'science'`）を評価します。候補が少ないときはドキュメントごとにフィルタを適用し、フィルタの選択性が高いときはフィルタのビットマップと直接積集合を取る高速パスを使います。

6. **verify_text** -- 候補を保存済みの正規化テキストと照合し、偽陽性を除くオプションのポストフィルタです（後述）。

7. **ソートとページネーション** -- 指定されたカラムでソートし、OFFSET/LIMIT で結果を切り出します。

複数の論理式の枝に同じ語が現れても、参照は 1回で済みます。重複を除いた検索語ごとの参照情報を、Boolean 式の評価、NOT の除外、同義語の展開、照合で共有します。通常の `NOT` は、一致するドキュメントを候補集合から取り除きます。集合の補集合が必要な式だけが、全 DocID を列挙します。`memory.verify_text` を設定している場合、除外する語も保存済みテキストで確認してから、ドキュメントを取り除きます。

テキストを多く読む処理にもメモリ境界があります。候補テキストは DocumentStore から上限付きのチャンクでコピーし、BM25 スコアリング、出現頻度の集計、テキストのポストフィルタを実行する前にストアのロックを解放します。そのため、候補が多くてもコーパスの大部分を一度にコピーしたり、スコアリング中ずっとストアをロックしたりしません。

## verify_text ポストフィルタ

N-gram インデックスによる検索は、本質的に近似です。`"quantum"` のクエリはバイグラム `["qu", "ua", "an", "nt", "tu", "um"]` を生成します。6つのバイグラムをすべて含むドキュメントが候補になりますが、一部は偽陽性です。

::: info 用語補足
**偽陽性**は、候補には入ったものの、実際には検索語を含んでいない結果です。N-gram 検索は速度を優先して候補を集め、`verify_text` が、正規化した検索語が部分文字列として含まれない候補を保存済みテキストとの照合で除きます。
:::

<DocDiagram name="verify-text" alt="verify_text が N-gram の積集合で得た候補を保存済み正規化テキストと照合し、偽陽性を除去してから結果を返す流れ" />

| ドキュメントテキスト | 全バイグラムを含む？ | 実際に"quantum"を含む？ |
|-------------------|-------------------|---------------------|
| "quantum mechanics" | はい | はい |
| "quantify antum" | はい（`qu`, `ua` は"quantify"から、`an`, `nt`, `tu`, `um` は"antum"から） | いいえ |

照合しない場合、110万件の Wikipedia 記事に対する `"quantum"` クエリは約 58,000件の候補を返します。`verify_text: all` を有効にすると、保存済みの正規化テキストとの部分文字列照合で 1,961件まで絞り込まれます。このクエリでは MySQL FULLTEXT と同じ件数でしたが、すべてのクエリで同じ意味論になるとは限りません。

MygramDB は、ハイライトなどの機能のために正規化テキストをメモリに保持します。`verify_text` がクエリに適用される場合は、ポスティングリストの積集合で得た各候補を保存済みテキストと照合し、偽陽性を破棄します。

[公開ベンチマーク](/ja/benchmarks)では、110 万件の記事のドキュメントストアとテキストストアの合計が約 1.78 GB でした。`verify_text` が制御するのは候補の照合であり、テキストの保存ではありません。モードは次の 3つです。

- `off`（デフォルト） -- 後段の照合なし。保存済みテキストはハイライトに利用できます。
- `ascii` -- ASCII のみのクエリを、保存済みテキストと照合して検証します。
- `all` -- 対象となるすべての候補について、検索語を保存済みの正規化テキストと照合します。

::: tip verify_text の選び方
正規化した部分文字列との照合が必要な場合は `verify_text: all` を選びます。MySQL FULLTEXT と同じ検索意味論を保証する設定ではありません。ハイライトはどのモードでも保存済みテキストを読みます。N-gram の候補検索で十分なら、後段の照合を行わない `off` を選べます。
:::

## キャッシュと無効化

MygramDB は検索結果をクエリ単位でキャッシュします。各エントリの依存関係を無効化用のメタデータとして記録するため、行が変わっても、テーブル全体ではなく影響するエントリだけを捨てます。

::: tip キャッシュ無効化とは
データが更新されたときに、古い検索結果を返さないようキャッシュを捨てる処理です。MygramDB は、変更された行が含む N-gram を調べ、それに関係するキャッシュ済みクエリだけを捨てます。
:::

binlog レプリケーションでドキュメントが挿入・更新・削除されると、次の順に処理します。

1. 変更されたドキュメントのテキストを N-gram に分割します。
2. 変更された N-gram と重複する N-gram セットを持つエントリを無効化します。フィルタカラムが変わったときはフィルタ付きエントリを直接探し、NOT を含むクエリなどテキスト変化に敏感なエントリも直接探します。
3. 無関係なクエリはキャッシュに残ります。

検索結果をキャッシュへ登録する前に、無効化の登録が引き続き有効か、取得済みのテーブルデータバージョンが変わっていないかを再確認します。結果に影響する書き込みがあった場合や、実行中にバージョンが変わった場合は、登録を拒否して `cache_rejections` を増やします。レプリケーションが有効なときは、キャッシュをレプリケーションの無効化処理に接続するまで、TCP リクエストの処理を待機させます。これにより、無効化の追跡対象になっていないキャッシュエントリが、起動中に返されることを防ぎます。

<DocDiagram name="cache-invalidation" alt="変更行が N-gram qu・ua・an にトークン化され、逆引きインデックス経由でキャッシュ済みの「quantum」だけが破棄され、「algorithm」と「database」は保持されることを示す図" />

- `quantum` — N-gram が重複するため無効化
- `algorithm`, `database` — 影響なし、キャッシュ維持

無効化されるエントリ数は、変更されたテキストやフィルタ、キャッシュ済みのクエリによって変わります。頻出語やテキスト変化に敏感なクエリは、多数のエントリに影響することがあります。それでも無効化マネージャはキャッシュ全体を破棄せず、該当する依存関係を持つエントリだけを対象にします。

無効化マネージャは N-gram、フィルタ付きエントリ、テキスト変化に敏感なエントリごとに逆引きインデックスを持ちます。そのため各トリガーは影響するエントリだけを調べ、キャッシュ全体を走査しません。キャッシュ保守も同じ考え方です。LRU リストを 1回で全走査せず、再開位置を記録した上限付きの範囲を定期保守の各回で処理するため、期限切れ確認や最近使用した項目の更新で長時間の排他処理になりません。

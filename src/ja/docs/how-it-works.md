# 仕組み

MygramDBはN-gramインデックスを中心に構築されたインメモリ全文検索エンジンです。このページでは、テキストのインデックス方法、検索の実行過程、キャッシュの整合性維持について解説します。

::: info 初めて読む場合
このページでは内部構造を説明します。まずは「文字列をN-gramに分ける」「N-gramから候補ドキュメントを探す」「必要なら保存済みの正規化テキストで確認する」という3段階だけ押さえれば十分です。
:::

## N-gramインデックス

MygramDBはテキストをN-gram（重複する文字列の断片）に分割します。デフォルトではASCIIテキストとCJKの漢字のどちらにも**バイグラム**（2文字）を使用します。CJKの漢字だけ別の長さにするには `kanji_ngram_size` を設定します。

::: info 用語補足
**トークン化**は、検索しやすいようにテキストを小さな単位へ分ける処理です。MygramDBは辞書を使わず、文字の並びそのものをN-gramとして扱います。
:::

例えば、`search`という単語は以下のバイグラムに分割されます：

```
"search" → ["se", "ea", "ar", "rc", "ch"]
```

`東京都`のような日本語文字列も、デフォルト設定ではバイグラムになります：

```
"東京都" → ["東京", "京都"]
```

各N-gramは**ポスティングリスト**（そのN-gramを含むドキュメントIDのソート済みリスト）に対応します。ドキュメントが挿入されると、テキストがトークン化され、各N-gramのポスティングリストにドキュメントIDが追加されます。

<DocDiagram name="ngram-index" alt="「search」がバイグラム se・ea・ar・rc・ch に分割され、それぞれが DocID 昇順のポスティングリストに対応し、文書1と42がすべてのリストに現れて積集合に残ることを示す図" />

ドキュメントIDは`uint32_t`型で、テーブルあたり最大40億件のドキュメントに対応します。

## ポスティングリスト圧縮

N-gramの出現頻度は均一ではありません。MygramDBはポスティングリストをデルタエンコーディングまたはRoaring ビットマップで保持します。`OPTIMIZE` は密度に応じて形式を選びますが、追加時の件数による自動変換もあります：

| 戦略 | 使用条件 | 表現方法 |
|------|---------|---------|
| **デルタエンコーディング** | 疎なリスト（`OPTIMIZE` 後の密度が通常18%未満） | ソート済みIDを固定幅の差分で格納 |
| **Roaring ビットマップ** | 密なリスト（`OPTIMIZE` 後の密度が通常18%以上）、または4,096件を超えるリスト | CRoaringライブラリによる圧縮ビットマップ |

**密度**の定義：`（そのN-gramを含むドキュメント数）/（テーブル内の全ドキュメント数）`

`OPTIMIZE` ではデフォルト18%の密度閾値と**0.5倍のヒステリシス**を使います。挿入によってデルタエンコーディングのリストが4,096件を超えると、密度に関係なくRoaringへ自動変換します。Roaringから戻るのは、件数が4,096以下かつ密度が閾値の半分（デフォルト9%）未満の場合です。

::: info 用語補足
**ヒステリシス**は、状態が頻繁に行ったり来たりしないように戻り条件をずらす考え方です。`OPTIMIZE` では18%でRoaringへ切り替え、9%未満で戻すことで、密度が境界付近にある場合の形式変更を抑えます。
:::

デルタエンコーディングは出現頻度の低い語に対してコンパクトです。`[100, 105, 200]`を`[100, 5, 95]`として格納します。Roaring ビットマップは頻出語に対してより効率的で、検索時のSIMDアクセラレーションによる集合演算（積集合、和集合）を可能にします。

## 検索パイプライン

検索クエリは以下の段階を順に通過します：

<DocDiagram name="search-pipeline" alt="クエリ受信、解析、N-gram 生成、ポスティングリストの積集合、NOT 除外、カラムフィルタ、verify_text ポストフィルタ、ソート、OFFSET と LIMIT、DocID 返却という10段階のパイプライン図" />

**各ステップの詳細：**

1. **クエリ解析** -- 検索語、NOT語、フィルタ条件、ソート順、ページネーションをクエリから抽出します。

2. **N-gram生成** -- 各検索語はUnicode正規化（ICUによるNFKC）の後、N-gramに分割されます。語は推定結果サイズの昇順にソートされ（最小のポスティングリストから処理）、中間結果セットを最小化します。

3. **ポスティングリストの積集合** -- 各語について、必要なN-gramポスティングリストの積集合を取ります（AND意味論）。次に、語間の結果を積集合します。最小のセットから開始することで、以降の積集合演算が高速になります。

4. **NOTフィルタ** -- NOT語にマッチするドキュメントを候補セットから除外します。

5. **カラムフィルタ** -- フィルタ条件（例：`category = 'science'`）を評価します。候補セットが小さい場合はドキュメントごとにフィルタを適用し、フィルタの選択性が高い場合はビットマップの直接積集合による高速パスを使用します。

6. **verify_text** -- 候補を保存済みの正規化テキストと照合し、偽陽性を除去するオプションのポストフィルタ（後述）。

7. **ソートとページネーション** -- 指定されたカラムでソートし、OFFSET/LIMITで結果を切り出します。

同じ語が複数の論理式の枝に現れても、検索パイプラインは同じ調査を繰り返しません。重複を除いた検索語ごとの参照情報を、論理式の評価、NOT の除外、同義語の展開、照合で共有します。通常の `NOT` は候補集合から一致する文書を除外します。集合の補集合が必要な式だけが全 DocID を列挙します。`memory.verify_text` の設定に従い、除外する語も保存済みテキストで確認してから文書を取り除きます。

テキストを多く読む処理にもメモリ境界があります。候補テキストは DocumentStore から上限付きのチャンクでコピーし、BM25 スコアリング、出現頻度の集計、テキストのポストフィルタを実行する前にストアのロックを解放します。そのため、候補が多くてもコーパスの大部分を一度にコピーしたり、スコアリング中ずっとストアをロックしたりしません。

## verify_text ポストフィルタ

N-gramインデックスは本質的に近似的です。`"quantum"`のクエリはバイグラム`["qu", "ua", "an", "nt", "tu", "um"]`を生成します。これらのバイグラムを含むドキュメントが候補になりますが、一部は偽陽性です：

<DocDiagram name="verify-text" alt="verify_text が N-gram の積集合で得た候補を保存済み正規化テキストと照合し、偽陽性を除去してから結果を返す流れ" />

::: info 用語補足
**偽陽性**は「候補には入ったが、実際には検索語を含んでいない結果」です。N-gram検索では候補を集め、`verify_text` を使うと正規化した検索語が部分文字列として含まれない候補を除けます。
:::

| ドキュメントテキスト | 全バイグラムを含む？ | 実際に"quantum"を含む？ |
|-------------------|-------------------|---------------------|
| "quantum mechanics" | はい | はい |
| "quantify antum" | はい（`qu`, `ua`は"quantify"から、`an`, `nt`, `tu`, `um`は"antum"から） | いいえ |

検証なしの場合、110万件のWikipedia記事に対する`"quantum"`クエリは約58,000件の候補を返します。`verify_text: all`を有効にすると、保存済みの正規化テキストとの部分文字列照合で1,961件まで絞り込まれます。このクエリではMySQL FULLTEXTと同じ件数でしたが、すべてのクエリで同じ意味論になることを保証しません。

**仕組み：** MygramDB はハイライトなどの機能のために正規化テキストをメモリに保持します。`verify_text` がクエリに適用される場合、ポスティングリストの積集合で得た候補を保存済みテキストと照合し、偽陽性を破棄します。

[公開ベンチマーク](/ja/benchmarks)では、110 万件の記事のドキュメントストアとテキストストアの合計が約 1.78 GB でした。`verify_text` が制御するのは候補の照合であり、テキストの保存ではありません。次の 3 モードがあります。

- `off`（デフォルト） -- 後段の照合なし。保存済みテキストはハイライトに利用できます。
- `ascii` -- ASCII のみのクエリを保存テキストと照合して検証します。
- `all` -- 対象となるすべての候補について、検索語を保存済みの正規化テキストと照合します。

::: tip verify_text の選び方
正規化した部分文字列との照合が必要な場合は `verify_text: all` を選びます。MySQL FULLTEXT と同じ検索意味論を保証する設定ではありません。ハイライトはどのモードでも保存済みテキストを読みます。N-gram の候補検索で十分なら、後段の照合を行わない `off` を選べます。
:::

## キャッシュと無効化

MygramDBはクエリレベルで検索結果をキャッシュします。各エントリが依存関係を無効化用メタデータとして持つため、行の変更ではテーブル全体ではなく影響するエントリだけを捨てます。

::: tip キャッシュ無効化とは
データが更新されたとき、古い検索結果を返さないようにキャッシュを捨てる処理です。MygramDBは影響を受けるN-gramだけを見て、関係する検索結果だけを捨てます。
:::

binlogレプリケーション経由でドキュメントが挿入・更新・削除されると：

1. 変更されたドキュメントのテキストをN-gramに分割します。
2. 変更された N-gram と重複する N-gram セットを持つエントリを無効化します。フィルタカラムが変わったときはフィルタ付きエントリを直接探し、NOT を含むクエリなどテキスト変化に敏感なエントリも直接探します。
3. 無関係なクエリはキャッシュに残ります。

検索結果をキャッシュへ登録する前に、無効化登録が引き続き有効か、取得済みのテーブルデータバージョンが変わっていないかを再確認します。結果に影響する書き込みや、実行中のバージョン変更があれば登録を拒否し、`cache_rejections` を増やします。レプリケーション有効時は、キャッシュをレプリケーションの無効化処理へ接続するまで、TCP リクエストの処理を待機させます。これにより、起動中に無効化処理へ接続していないキャッシュの結果が返ることを防ぎます。

<DocDiagram name="cache-invalidation" alt="変更行が N-gram qu・ua・an にトークン化され、逆引きインデックス経由でキャッシュ済みの「quantum」だけが破棄され、「algorithm」と「database」は保持されることを示す図" />

- `quantum` — N-gram が重複するため無効化
- `algorithm`, `database` — 影響なし、キャッシュ維持

無効化される件数は、変更されたテキストやフィルタ、キャッシュ済みのクエリによって変わります。頻出語やテキスト変化に敏感なクエリが多ければ、多数のエントリが影響を受けます。無効化マネージャはキャッシュ全体を破棄せず、該当する依存関係を持つエントリを探します。

無効化マネージャは N-gram、フィルタ付きエントリ、テキスト変化に敏感なエントリごとに逆引きインデックスを持ちます。そのため各トリガーは影響するエントリだけを調べ、キャッシュ全体を走査しません。キャッシュ保守も同じ考え方です。LRU リストを1回で全走査せず、再開位置を記録した上限付きの範囲を定期保守の各回で処理するため、期限切れ確認や最近使用した項目の更新で長時間の排他処理になりません。

# 仕組み

MygramDBはN-gramインデックスを中心に構築されたインメモリ全文検索エンジンです。このページでは、テキストのインデックス方法、検索の実行過程、キャッシュの整合性維持について解説します。

::: info 初めて読む場合
このページでは内部構造を説明します。まずは「文字列をN-gramに分ける」「N-gramから候補ドキュメントを探す」「必要なら原文で確認する」という3段階だけ押さえれば十分です。
:::

## N-gramインデックス

MygramDBはテキストをN-gram（重複する文字列の断片）に分割します。デフォルトではASCIIテキストとCJKの漢字のどちらにも**バイグラム**（2文字）を使用します。CJKの漢字だけ別の長さにするには `kanji_ngram_size` を設定します。

::: info 用語補足
**トークン化**は、検索しやすいようにテキストを小さな単位へ分ける処理です。MygramDBは辞書を使わず、文字の並びそのものをN-gramとして扱います。
:::

例えば、`search`という単語は以下のバイグラムに分割されます：

```
"search" → ["se", "ea", "ar", "rc", "ch"]
```

`東京都`のような日本語文字列も、デフォルト設定ではバイグラムになります：

```
"東京都" → ["東京", "京都"]
```

各N-gramは**ポスティングリスト**（そのN-gramを含むドキュメントIDのソート済みリスト）に対応します。ドキュメントが挿入されると、テキストがトークン化され、各N-gramのポスティングリストにドキュメントIDが追加されます。

<DocDiagram name="ngram-index" alt="「search」がバイグラム se・ea・ar・rc・ch に分割され、それぞれが DocID 昇順のポスティングリストに対応し、文書1と42がすべてのリストに現れて積集合に残ることを示す図" />

ドキュメントIDは`uint32_t`型で、テーブルあたり最大40億件のドキュメントに対応します。

## ポスティングリスト圧縮

N-gramの出現頻度は均一ではありません。MygramDBは2つのストレージ戦略を使い分け、密度に基づいて自動的に切り替えます：

| 戦略 | 使用条件 | 表現方法 |
|------|---------|---------|
| **デルタエンコーディング** | 疎な語（密度 < 18%） | ソート済みIDを固定幅の差分で格納 |
| **Roaringビットマップ** | 密な語（密度 >= 18%） | CRoaringライブラリによる圧縮ビットマップ |

**密度**の定義：`（そのN-gramを含むドキュメント数）/（テーブル内の全ドキュメント数）`

18%の閾値には**0.5倍のヒステリシス**が設けられており、頻繁な切り替えを防止します。18%でRoaringに切り替わったポスティングリストは、密度が9%を下回るまでデルタエンコーディングには戻りません。

::: info 用語補足
**ヒステリシス**は、状態が頻繁に行ったり来たりしないように戻り条件をずらす考え方です。ここでは18%でRoaringへ切り替え、9%未満になるまで戻さないことで、更新のたびに形式が揺れるのを防ぎます。
:::

デルタエンコーディングは出現頻度の低い語に対してコンパクトです。`[100, 105, 200]`を`[100, 5, 95]`として格納します。Roaringビットマップは頻出語に対してより効率的で、検索時のSIMDアクセラレーションによる集合演算（積集合、和集合）を可能にします。

## 検索パイプライン

検索クエリは以下の段階を順に通過します：

<DocDiagram name="search-pipeline" alt="クエリ受信、解析、N-gram 生成、ポスティングリストの積集合、NOT 除外、カラムフィルタ、verify_text ポストフィルタ、ソート、OFFSET と LIMIT、DocID 返却という10段階のパイプライン図" />

**各ステップの詳細：**

1. **クエリ解析** -- 検索語、NOT語、フィルタ条件、ソート順、ページネーションをクエリから抽出します。

2. **N-gram生成** -- 各検索語はUnicode正規化（ICUによるNFKC）の後、N-gramに分割されます。語は推定結果サイズの昇順にソートされ（最小のポスティングリストから処理）、中間結果セットを最小化します。

3. **ポスティングリストの積集合** -- 各語について、必要なN-gramポスティングリストの積集合を取ります（AND意味論）。次に、語間の結果を積集合します。最小のセットから開始することで、以降の積集合演算が高速になります。

4. **NOTフィルタ** -- NOT語にマッチするドキュメントを候補セットから除外します。

5. **カラムフィルタ** -- フィルタ条件（例：`category = 'science'`）を評価します。候補セットが小さい場合はドキュメントごとにフィルタを適用し、フィルタの選択性が高い場合はビットマップの直接積集合による高速パスを使用します。

6. **verify_text** -- 候補を原文と照合し偽陽性を除去するオプションのポストフィルタ（後述）。

7. **ソートとページネーション** -- 指定されたカラムでソートし、OFFSET/LIMITで結果を切り出します。

同じ語が複数の論理式の枝に現れても、検索パイプラインは同じ調査を繰り返しません。重複を除いた term info の参照結果を、論理式の評価、NOT の除外、同義語の展開、照合で共有します。式に NOT がない場合は、全 DocID を走査しません。

テキストを多く読む処理にもメモリ境界があります。候補テキストは DocumentStore から上限付きのチャンクでコピーし、BM25 スコアリング、出現頻度の集計、テキストのポストフィルタを実行する前にストアのロックを解放します。そのため、候補が多くてもコーパスの大部分を一度にコピーしたり、スコアリング中ずっとストアをロックしたりしません。

## verify_text ポストフィルタ

N-gramインデックスは本質的に近似的です。`"quantum"`のクエリはバイグラム`["qu", "ua", "an", "nt", "tu", "um"]`を生成します。これらのバイグラムを含むドキュメントが候補になりますが、一部は偽陽性です：

<DocDiagram name="verify-text" alt="verify_text が N-gram の積集合で得た候補を保存済み正規化テキストと照合し、偽陽性を除去してから結果を返す流れ" />

::: info 用語補足
**偽陽性**は「候補には入ったが、実際には検索語を含んでいない結果」です。N-gram検索では高速化のためにまず広めに候補を集め、`verify_text` で必要に応じて正確に絞り込みます。
:::

| ドキュメントテキスト | 全バイグラムを含む？ | 実際に"quantum"を含む？ |
|-------------------|-------------------|---------------------|
| "quantum mechanics" | はい | はい |
| "quantify antum" | はい（`qu`, `ua`, `an`, `nt`, `tu`は"quantify"から、`an`, `nt`, `tu`, `um`は"antum"から） | いいえ |

検証なしの場合、110万件のWikipedia記事に対する`"quantum"`クエリは約58,000件の候補を返します。`verify_text: all`を有効にすると、原文照合で1,961件まで絞り込まれ、MySQL FULLTEXTの結果と一致します。

**仕組み：** `verify_text`が有効な場合、MygramDBは原文テキストをメモリに保持します。ポスティングリストの積集合で候補が得られた後、各候補の保存テキストに対して実際の部分文字列一致を確認し、偽陽性を破棄します。

トレードオフはメモリです。110万件のドキュメントのテキスト保存に約1.5 GBのRAMが追加で必要です。3つのモードが利用可能です：

- `off`（デフォルト） -- テキスト保存なし、検証なし。最速・最小メモリ。
- `ascii` -- ASCIIのみのクエリを保存テキストと照合して検証。メモリ使用量は中程度。
- `all` -- すべての候補を検証。正確性を優先。

::: tip verify_text の選び方
正確な一致やハイライト、BM25 `_score` を重視する場合は `verify_text: all` が分かりやすい選択です。メモリを最小化したい場合や候補検索で十分な用途では `off` も選択肢になります。
:::

## キャッシュと無効化

MygramDBはクエリレベルで検索結果をキャッシュします。各エントリが依存関係を無効化用メタデータとして持つため、行の変更ではテーブル全体ではなく影響するエントリだけを捨てます。

::: tip キャッシュ無効化とは
データが更新されたとき、古い検索結果を返さないようにキャッシュを捨てる処理です。MygramDBは影響を受けるN-gramだけを見て、関係する検索結果だけを捨てます。
:::

binlogレプリケーション経由でドキュメントが挿入・更新・削除されると：

1. 変更されたドキュメントのテキストをN-gramに分割します。
2. 変更された N-gram と重複する N-gram セットを持つエントリを無効化します。フィルタカラムが変わったときはフィルタ付きエントリを直接探し、NOT を含むクエリなどテキスト変化に敏感なエントリも直接探します。
3. 無関係なクエリはキャッシュに残ります。

<DocDiagram name="cache-invalidation" alt="変更行が N-gram qu・ua・an にトークン化され、逆引きインデックス経由でキャッシュ済みの「quantum」だけが破棄され、「algorithm」と「database」は保持されることを示す図" />

- `quantum` — N-gram が重複するため無効化
- `algorithm`, `database` — 影響なし、キャッシュ維持

これにより、1行の更新は影響を受ける可能性のあるクエリのみを無効化します。数百万のキャッシュエントリがあるテーブルでも、更新で無効化されるのはわずか数件程度です。

無効化マネージャは N-gram、フィルタ付きエントリ、テキスト変化に敏感なエントリごとに逆引きインデックスを持ちます。そのため各トリガーは影響するエントリだけを調べ、キャッシュ全体を走査しません。キャッシュ保守も同じ考え方です。LRU リストを1回で全走査せず、再開位置を記録した上限付きの範囲を各 tick で処理するため、期限切れ確認や最近使用した項目の更新で長時間の排他処理になりません。

# 用語集

MygramDB のドキュメントで使う用語をまとめています。細かい実装名をすべて覚える必要はありません。まずは「MySQL から変更を受け取り、メモリ上の検索インデックスを更新する仕組み」と捉えれば十分です。

::: tip 最初に押さえる用語
初めてセットアップする場合は、まず **binlog**、**GTID**、**初期スナップショット**、**N-gram**、**CIDR** の 5つを押さえれば進められます。
:::

## MySQL / レプリケーション

### binlog

MySQL や MariaDB が、INSERT/UPDATE/DELETE などの変更履歴を書き出すログです。MygramDB はこのログを読んで、MySQL 側の変更を検索インデックスへ反映します。

### ROW 形式

binlog に「どの行がどう変わったか」を記録する形式です。MygramDB は行単位の変更を読むため、`binlog_format=ROW` が必要です。

### binlog_row_image=FULL

UPDATE/DELETE 時に、変更前後の行データを十分に含める設定です。MygramDB がテキストカラムやフィルタカラムを正しく更新・削除するために必要です。

### binlog_row_metadata=FULL

MySQL または MariaDB のソースサーバーで、カラム名などのオプションメタデータを `TABLE_MAP` イベントに含める設定です。MygramDB はイベントに記録された定義を使い、行が書き込まれた時点のテーブル構造に基づいてデコードします。

### GTID

MySQL のトランザクションに付く一意な番号です。「どこまで変更を読んだか」を安全に記録するために使います。MygramDB はダンプファイルに GTID を保存し、再起動後にその位置から追いつきます。MySQL 8.4 以降では、タグ付きの GTID（`UUID:tag:txn`）も使えます。詳しくは[タグ付き GTID](/ja/docs/replication#start-from-gtid) を参照してください。

### レプリカ

MySQL の変更を受け取る側のサーバーです。MygramDB は MySQL から見ると検索専用のレプリカのように振る舞いますが、SQL クエリを実行する一般的な MySQL レプリカではありません。

### レプリケーション遅延

MySQL でコミットされた変更が、MygramDB で検索できるようになるまでの遅れです。遅延が大きいと、検索結果に最新の書き込みが反映されません。

### 初期スナップショット

MySQL 上の既存データを最初に読み込んで、MygramDB の検索インデックスを作る処理です。通常は `SYNC <table>` で明示的に開始します。MySQL からの読み込みであり、ファイルではありません。ファイルとの違いは[スナップショット / ダンプ](#%E3%82%B9%E3%83%8A%E3%83%83%E3%83%95%E3%82%9A%E3%82%B7%E3%83%A7%E3%83%83%E3%83%88-%E3%82%BF%E3%82%99%E3%83%B3%E3%83%95%E3%82%9A)を参照してください。

## 検索インデックス

### N-gram

文字列を固定長の小さな断片に分けたものです。たとえば `search` を 2文字単位にすると `se`、`ea`、`ar`、`rc`、`ch` になります。MygramDB はこの断片を手がかりに高速検索します。

### CJK

CJK は Chinese、Japanese、Korean の略です。MygramDB のインデックス設定では、CJK は「東京」のような漢字系表意文字を指し、中国語・日本語・韓国語で使うすべての文字を指すわけではありません。これらの文字を分割する長さは `kanji_ngram_size` で設定します。

### ポスティングリスト

ある N-gram を含むドキュメント ID の一覧です。たとえば `se` を含むドキュメントが 1、5、42 なら、`se -> [1, 5, 42]` のように持ちます。

### ドキュメントストア

テーブルごとに持つ保存領域です。DocID と MySQL の主キーを対応付け、フィルタカラムの値と正規化テキストを保持します。インデックスが候補を見つけ、ドキュメントストアが結果を返したり絞り込んだりします。

### DocID

MygramDB 内部で使う数値 ID です。MySQL の主キーとは別物です。検索処理では DocID を使い、結果を返すときに MySQL の主キーへ戻します。

### Roaring ビットマップ

整数の集合を圧縮するデータ構造です。ID を複数の範囲に分け、範囲ごとに配列やビットマップなどの表現を選びます。MygramDB は密なポスティングリストに使いますが、実際のメモリ使用量は ID の分布やワークロードで変わります。

### デルタエンコーディング

連続する ID をそのまま保存せず、前の ID との差分で保存する圧縮方法です。`100, 105, 200` を `100, 5, 95` のように表せるため、疎なポスティングリストでメモリを節約できます。

### BM25

検索語がドキュメント内でどれだけ重要かをスコア化する、代表的な全文検索のランキング方式です。MygramDB では `bm25.enable: true` を設定すると、`SORT _score DESC` で関連度順に並べ替えられます。

### verify_text

N-gram 検索で得た候補を、保存済みの正規化テキストと照合し、正規化した検索語が部分文字列として含まれない候補を除く機能です。MySQL FULLTEXT と同じ意味論を保証するものではありません。対象候補すべてを照合する場合は `memory.verify_text: "all"` を使います。

### 同義語

クエリに追加する別の語句です。同義語を設定すると、関連する表現も含めて検索できます。

### SIMD

Single Instruction, Multiple Data の略です。CPU のベクトル命令を使い、1つの演算を複数の値にまとめて適用します。CRoaring はビルドと CPU が対応する場合、ビットマップ演算に利用できます。

### ファセット

検索結果をカテゴリやステータスなどの値ごとに集計する機能です。たとえば「検索結果のうち category=tech が 15件、ops が 7件」のような件数を返します。

## API / 運用

### TCP プロトコル

MygramDB 独自のテキストベースのコマンドプロトコルです。`SEARCH articles hello` のようなコマンドを TCP ポート 11016 へ送ります。

### HTTP API

JSON で検索・カウント・ファセット・ドキュメント取得を行う API です。テーブル操作には `/tables/{identity}/...` を使います。`q` はデフォルトでリテラル文字列として検索します。Boolean 検索の構文を使うには `"mode": "boolean"` を指定します。

### CIDR

IP アドレスの範囲表現です。`10.0.0.0/8` は `10.` で始まる広い範囲を表します。MygramDB は `network.allow_cidrs` を許可リストとして使い、接続できるクライアントを制限します。

### CORS

ブラウザから別ドメインの HTTP API を呼ぶための仕組みです。サーバー間通信では通常不要です。ブラウザから直接 MygramDB を呼ぶ場合だけ、信頼できる Origin に限定して有効にしてください。非公開の API にワイルドカードは使わないでください。

### 管理トークン

`api.admin_token` に設定する秘密の値です。設定すると、`DUMP SAVE` などの管理コマンドを実行する前にクライアントの認証が必要になります。

### スナップショット / ダンプ

この 2つは別のものを指します。[初期スナップショット](#%E5%88%9D%E6%9C%9F%E3%82%B9%E3%83%8A%E3%83%83%E3%83%95%E3%82%9A%E3%82%B7%E3%83%A7%E3%83%83%E3%83%88)は、MySQL から読み込んでインデックスを作る処理です。**ダンプファイル**は、MygramDB 自身がインデックス、ドキュメントストア、GTID 位置を書き出したファイルです。`DUMP SAVE` で作成し、`DUMP LOAD` で復元します。詳しくは[スナップショットとダンプ復旧](/ja/docs/snapshot)を参照してください。

### WAL

Write-Ahead Log の略で、データベースが変更履歴を先にログへ書く方式です。MygramDB は WAL を使わず、ダンプファイルと MySQL binlog の再読込で復旧します。

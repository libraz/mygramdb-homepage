# アーキテクチャ

MygramDB は MySQL（8.4/9.7/26.x）または MariaDB（10.11+/11.x/12.x）の横に置くサイドカープロセスとして動作します。接続先サーバーの binlog（バイナリログ）を読み取り、インメモリの全文インデックスを構築・維持して、TCP と HTTP で検索クエリに応答します。サーバー種別は機能プローブで判定するため、同じバイナリと設定でどちらにも対応できます。

<DocDiagram name="system-flow" alt="MySQLを正本として残し、MygramDBがスナップショットとbinlogを読み取ってインメモリ検索インデックスを維持し、TCPまたはHTTPで検索に応答する構成図" />

責務の境界は次のとおりです。MySQL/MariaDB は書き込みと通常の SQL を扱う永続データの正本です。MygramDB が持つのは検索用のインデックスで、初期スナップショットと binlog の再生から再構築できます。

::: info 用語補足
**サイドカー**は、既存のシステムを置き換えず、その横に置いて特定の役割だけを担うプロセスです。ここでは、MySQL が書き込みと通常の SQL を、MygramDB が全文検索を担当します。
:::

## システム概要

::: info 用語補足
**インデックス**は検索候補を速く見つけるための構造です。**ドキュメントストア**（`DocumentStore`）は、結果を返したり絞り込んだりするために必要な主キー、フィルタ値、正規化テキストを持つ構造です。検索用と取得用で最適化の方向が違うため、意図的に分けています。
:::

<DocDiagram name="component-flow" alt="MySQL が BinlogReader へ、BinlogReader がインメモリの Index と DocStore へ、SearchHandler が TCP・HTTP クライアントへ応答し、スナップショットファイルを定期ダンプ・起動時読み込みする内部構成図" />

**コンポーネント**

- **BinlogReader** -- MySQL にレプリカとして接続し、GTID ベースの binlog ストリームを受信します。受け取ったバイト列は、別ライブラリの [libmybinlog](/ja/docs/binlog-decoding) が行レベルのイベント（INSERT、UPDATE、DELETE）にデコードします。
- **Index** -- インメモリの N-gram インデックスです。N-gram 文字列を、ポスティングリスト（ソート済みのドキュメント ID の集合）へ対応付けます。
- **DocumentStore** -- 内部 DocID と MySQL の主キーを対応付け、フィルタカラムの値と正規化テキストを保持します。フィルタカラム名はテーブルごとに一度だけ登録し、各ドキュメントはカラム ID をキーとする小さなベクトルに値を持ちます。ドキュメントごとにカラム名を重複して保存しないためです。
- **SearchHandler** -- クエリを解析し、検索パイプラインを実行し、クエリキャッシュを管理します。テキストを多く読む処理では候補テキストを上限付きのチャンクで取得します。
- **ダンプ** -- インデックスの状態と GTID 位置を定期的にダンプファイルへ書き出します。再起動時に全体を作り直さずに済みます。

## データフロー

MygramDB は 3つのフェーズで動作します。

### フェーズ 1：初期スナップショット

`SYNC` 実行時、または `replication.auto_initial_snapshot: true` が設定されている場合、MygramDB はソーステーブルを一貫性のあるスナップショットとして読み込みます。デフォルトは `auto_initial_snapshot: false` なので、初回の MySQL 読み取りのタイミングは自分で決めます。

次の図は MySQL での流れを示します。

<DocDiagram name="initial-snapshot-sequence" alt="MySQL では、MygramDB が整合スナップショットのトランザクション開始前に安全な下限 GTID を記録し、行をストリーム処理してインデックスを構築し、COMMIT 後に安全な位置から binlog を再開します。" />

MySQL では、トランザクション開始前の GTID を記録しておくことで、変更の取りこぼしを防ぎます。GTID の記録からトランザクション開始までの間にコミットされた変更は再適用されることがありますが、行への適用は冪等です。MariaDB では、スナップショットの binlog ファイルと位置をそのまま `BINLOG_GTID_POS` で GTID に変換します。ソースごとの動作は[スナップショットと binlog の引き継ぎ](/ja/docs/replication)を参照してください。

### フェーズ 2：ライブレプリケーション

初期スナップショット後、MygramDB は binlog ストリーミングに切り替わります。

<DocDiagram name="live-replication-sequence" alt="MySQL が行イベントを上限付きキューへ送り、ワーカーが1件ずつ取り出して Index と DocStore を更新し、影響するキャッシュを無効化するシーケンス図" />

BinlogReader スレッドがイベントを上限付きキューに読み込み、ワーカースレッドがそれを取り出してインデックスとドキュメントストアに適用します。キューは短時間の書き込み集中を吸収します。MySQL の書き込みが MygramDB の適用速度を継続して上回ると、レプリケーション遅延が増えます。

接続が切れると、設定済みの接続先へ再接続し、最後に適用または処理した GTID 位置から再開します。この位置より後のイベントは再送されることがありますが、冪等に適用されます。

### フェーズ 3：クエリ処理

検索クエリは TCP（ポート 11016、デフォルト）または HTTP（ポート 8080、デフォルトでは無効）で届き、[検索パイプライン](/ja/docs/how-it-works#%E6%A4%9C%E7%B4%A2%E3%83%8F%E3%82%9A%E3%82%A4%E3%83%95%E3%82%9A%E3%83%A9%E3%82%A4%E3%83%B3)を通して処理されます。

## スレッドモデル

MygramDB は TCP 接続に**イベント駆動 Reactor I/O モデル**を採用しています。Reactor は epoll（Linux）または kqueue（macOS）でイベントループ上の多数の接続を監視し、上限付きのワーカープールへ処理を渡します。処理できる接続数は、ワークロードと OS の制限で変わります。

::: info 用語補足
**Reactor I/O モデル**は、多数の接続を少数のスレッドで監視し、処理が必要になったときだけワーカーへ渡す方式です。接続ごとにスレッドを作らないため、アイドル接続が多くてもスレッドを消費しません。
:::

<DocDiagram name="thread-model" alt="メインスレッドが初期化と統括、Reactor スレッドが接続を多重化、BinlogReader スレッドがイベントキューへ供給し、ワーカープールが共有の Index と DocStore に対して読み取りロックと書き込みロックを取るスレッド構成図" />

**並行性モデル**

- **Reactor** スレッドがすべての TCP I/O（accept、read、write）を epoll/kqueue で処理します。接続ごとにスレッドを作る方式ではないため、数千のアイドル接続があってもスレッドを消費しません。
- 解析したリクエストは**ワーカースレッドプール**へ渡され、そこでクエリを実行します。
- Index と DocumentStore は、それぞれ自分の状態の同期を管理します。検索は必要なデータを取るために短い共有アクセスを行い、binlog イベントの適用は更新を調整してから新しい状態を公開します。
- 候補テキストは上限付きのチャンクで取り出します。BM25 スコアリング、出現頻度の集計、テキストのポストフィルタの前に DocumentStore のロックを解放するため、時間のかかる処理がストアをロックし続けません。
- キャッシュ無効化は、N-gram、フィルタ、テキスト変化に敏感な依存関係ごとの逆引きインデックスを使います。定期的な LRU 保守は、全エントリを 1回の排他ロックで走査せず、上限付きの範囲を順に処理します。
- コネクション単位の**バックプレッシャー**（`api.tcp.max_write_queue_bytes`、デフォルト 16 MiB）により、書き込みキューが上限を超えた低速クライアントを強制切断し、メモリ枯渇を防止します。
- 統計情報（クエリ数、キャッシュヒット数）にはアトミックカウンターを使い、ホットパスでのロック競合を避けます。

::: info 用語補足
**バックプレッシャー**は、遅いクライアントに合わせてサーバー側の送信待ちデータが増え続けないように制限する仕組みです。上限を超えた接続を切ることで、1つの接続がプロセス全体のメモリを使い切ることを防ぎます。
:::

すべてのスレッドはシャットダウン時に join され、デタッチされるスレッドはありません。

## 永続化

MygramDB は状態を定期的な**ダンプファイル**として永続化し、WAL（Write-Ahead Log）は使用しません。

::: info 用語補足
**WAL** は、変更を発生順にログへ書き込む方式です。MygramDB は MySQL を正本とするため、独自の WAL は持たず、定期ダンプと MySQL binlog からの追いつきで復旧します。
:::

<DocDiagram name="persistence-cycle" alt="メモリ上のインデックスと現在の GTID 位置をディスクのスナップショットファイルへ定期ダンプし、復旧時はそのダンプを読み込んでから保存済み GTID 以降の binlog を再適用する図" />

**仕組み**

1. バックグラウンドのスケジューラが、インデックス、ドキュメントストア、現在の GTID 位置を定期的にディスクへ書き出します。
2. `dump.load_on_startup: true` の場合、起動時に `dump.dir/default_filename` を読み込みます。復元に成功すると、保存済みの GTID からレプリケーションを再開します。この構成には `replication.start_from: snapshot` が必要です。
3. その GTID から MySQL の現在位置までのイベントを自動で適用します。ダンプの検証に失敗した場合は、MySQL から初期スナップショットを作成します。

ダンプの復元に成功しても MySQL の現在位置まで追いつけない場合、MygramDB は復元したインデックスで検索に応答し続け、レプリケーションは停止します。Readiness は `not_ready` を返します。復旧手順は[ダンプの保存と復旧](/ja/docs/snapshot)を参照してください。

ダンプの書き込みは**アトミックなファイル操作**（一時ファイルに書き込んでからリネーム）で行うため、書き込み中にプロセスが中断されてもファイルは壊れません。

起動時にダンプ復元を試みない構成では、`replication.auto_initial_snapshot` を有効にして初期インデックスを自動作成するか、`SYNC <table>`（複数 DB 構成では `SYNC <database>.<table>`）を実行します。起動時のダンプ復元に失敗した場合は、`auto_initial_snapshot` が false でも MySQL から初期スナップショットを作成します。

::: warning MySQL バックアップの代替ではありません
MygramDB のダンプファイルは、検索インデックスを素早く復旧するためのものです。MySQL 本体のバックアップやポイントインタイムリカバリは、MySQL 側で別途用意してください。
:::

## メモリレイアウト

<DocDiagram name="memory-layout" alt="テーブルごとに、インデックスが N-gram マップとポスティングリストを、ドキュメントストアが主キー、フィルタカラム、正規化テキストを保持し、共有キャッシュがクエリ結果と N-gram 逆引きインデックスを持つメモリ構成図" />

**サイジングの参考値。** 以下は公開している v1.10.0 のベンチマーク実測値です。110万件の Wikipedia 記事（英語 100万件・日本語 10万件、平均 666文字）を `verify_text: all` で、32 GiB のコンテナ上で計測しています。実行条件の全体は[ベンチマーク](/ja/benchmarks)をご覧ください。

| コンポーネント | メモリ |
|--------------|--------|
| Index（N-gram マップ + ポスティングリスト） | 約 152 MB |
| DocumentStore + テキストストア | 約 1.78 GB |
| **RSS 合計** | **約 3.41 GB** |

サーバーは `verify_text: off` でも正規化テキストを保持します。ハイライトをクエリごとに指定できるためです。`verify_text` が制御するのは後段の照合であり、テキストの保存ではありません。容量見積もりの方法は [FAQ](/ja/faq#mygramdb-に必要なメモリ量は) を参照してください。

テーブルごとに、フィルタカラムへ一度だけ ID を割り当てます。各ドキュメントはその ID をキーとする小さなベクトルに値を持つため、カラム名を重複して保存しません。

上記ベンチマークでは、保存されたテキストとドキュメントデータがメモリの大部分を占めます。メモリ使用量はデータに依存します。`OPTIMIZE` は密度に応じてデルタエンコーディングまたは Roaring ビットマップを選び、挿入時は 4,096件を超えたデルタ形式のリストも Roaring へ変換します。監視のたびに全テーブルをロックすることはなく、テーブルごとの値を上限付きのスナップショットへ集約して、`INFO`、`/metrics`、Prometheus に返します。詳しくは[仕組み](/ja/docs/how-it-works#%E3%83%9B%E3%82%9A%E3%82%B9%E3%83%86%E3%82%A3%E3%83%B3%E3%82%AF%E3%82%99%E3%83%AA%E3%82%B9%E3%83%88%E5%9C%A7%E7%B8%AE)をご覧ください。

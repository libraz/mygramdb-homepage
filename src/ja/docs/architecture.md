# アーキテクチャ

MygramDB は MySQL（8.4/9.x）または MariaDB（10.11+/11.x/12.x）の横に置くサイドカープロセスとして動作します。接続先サーバーのバイナリログを読み取り、インメモリ全文インデックスを構築・維持し、TCP および HTTP 経由で検索クエリに応答します。サーバー種別は機能プローブで判定するため、同じバイナリと設定でどちらでも動作します。

<DocDiagram name="system-flow" alt="MySQLを正本として残し、MygramDBがスナップショットとbinlogを読み取ってインメモリ検索インデックスを維持し、TCPまたはHTTPで検索に応答する構成図" />

重要なのは責務の境界です。MySQL/MariaDBは書き込みと通常のSQLを扱う永続データの正本であり、MygramDBはスナップショットとbinlog再生から再構築できる検索用インデックスを保持します。

::: info 用語補足
**サイドカー**は、既存のMySQLを置き換えず、横に追加して特定の役割だけを担うプロセスのことです。MygramDBの場合、MySQLは書き込みと通常のSQLを担当し、MygramDBは全文検索を担当します。
:::

## システム概要

<DocDiagram name="component-flow" alt="MySQL が BinlogReader へ、BinlogReader がインメモリの Index と DocStore へ、SearchHandler が TCP・HTTP クライアントへ応答し、スナップショットファイルを定期ダンプ・起動時読み込みする内部構成図" />

**コンポーネント：**

- **BinlogReader** -- MySQLにレプリカとして接続し、GTIDベースのbinlogストリーミングで行レベルイベント（INSERT, UPDATE, DELETE）を受信します。
- **Index** -- インメモリN-gramインデックス。N-gram文字列からポスティングリスト（ソート済みドキュメントIDの集合）へのマップです。
- **DocumentStore** -- 内部 DocID から MySQL 主キーへのマッピングを管理し、フィルタカラムの値と正規化テキストを保持します。フィルタカラム名はストアごとに1回だけインターンし、各ドキュメントは同じ名前を繰り返し持つ代わりにカラム ID 順の小さなベクトルを持ちます。
- **SearchHandler** -- クエリを解析し、検索パイプラインを実行し、クエリキャッシュを管理します。テキストを多く読む処理では候補テキストを上限付きのチャンクで取得します。
- **Snapshot** -- インデックス状態とGTIDポジションを定期的にディスクにダンプし、高速な再起動を実現します。

::: info 用語補足
**DocStore** は検索結果を返すための補助データ置き場です。インデックスは検索候補を速く見つけるための構造、DocStoreは主キーやフィルタ値など結果表示・絞り込みに必要な情報を持つ構造です。
:::

## データフロー

MygramDBは大きく3つのフェーズで動作します。

### フェーズ1：初期スナップショット

`SYNC` 実行時、または `replication.auto_initial_snapshot: true` が設定されている場合、MygramDBはソーステーブルの一貫性のあるスナップショットを取得します。デフォルトは `auto_initial_snapshot: false` なので、本番運用では初回MySQL読み取りのタイミングを明示的に選びます。

次の図は MySQL でのスナップショット取得を示します。

<DocDiagram name="initial-snapshot-sequence" alt="MySQL では、MygramDB が整合スナップショットのトランザクション開始前に安全な下限 GTID を記録し、行をストリーム処理してインデックスを構築し、COMMIT 後に安全な位置から binlog を再開します。" />

MySQL では、トランザクション開始前の GTID を使うことで変更の欠落を防ぎます。GTID 取得からトランザクション開始までのコミットは再適用されることがありますが、行への適用は冪等です。MariaDB では、スナップショット自体の正確な binlog ファイルと位置を `BINLOG_GTID_POS` で GTID に変換します。ソースごとの動作は[スナップショットと binlog の引き継ぎ](/ja/docs/replication)を参照してください。

### フェーズ2：ライブレプリケーション

初期スナップショット後、MygramDBはbinlogストリーミングに切り替わります：

<DocDiagram name="live-replication-sequence" alt="MySQL が行イベントを上限付きキューへ送り、ワーカーが1件ずつ取り出して Index と DocStore を更新し、影響するキャッシュを無効化するシーケンス図" />

BinlogReaderスレッドがイベントを上限付きキューに読み込み、ワーカースレッドがイベントを取り出してインデックスとドキュメントストアに適用します。この分離により、短いバースト時でもbinlogリーダーがMySQLの変更を読み進めやすくなります。

接続切断時は設定済みの接続先へ再接続し、最後に適用または処理した GTID ポジションから再開します。その後のイベントは再送され、冪等に適用されることがあります。

### フェーズ3：クエリ処理

検索クエリはTCP（ポート11016、デフォルト）またはHTTP（ポート8080、デフォルトでは無効）経由で到着し、[検索パイプライン](/ja/docs/how-it-works#%E6%A4%9C%E7%B4%A2%E3%83%8F%E3%82%9A%E3%82%A4%E3%83%95%E3%82%9A%E3%83%A9%E3%82%A4%E3%83%B3)を通して処理されます。

## スレッドモデル

MygramDBはTCP接続に**イベント駆動 Reactor I/O モデル**を採用しています。Reactorはepoll（Linux）またはkqueue（macOS）を使用して数千の接続を単一のイベントループスレッドで多重化し、上限付きのワーカープールにディスパッチします。

::: info 用語補足
**Reactor I/Oモデル**は、多数の接続を少数のスレッドで監視し、実際に処理が必要になったときだけワーカーへ渡す方式です。接続ごとにスレッドを作らないため、アイドル接続が多い環境でもスレッドを浪費しません。
:::

<DocDiagram name="thread-model" alt="メインスレッドが初期化と統括、Reactor スレッドが接続を多重化、BinlogReader スレッドがイベントキューへ供給し、ワーカープールが共有の Index と DocStore に対して読み取りロックと書き込みロックを取るスレッド構成図" />

**並行性モデル：**

- **Reactor**スレッドがすべてのTCP I/O（accept、read、write）をepoll/kqueueで処理します。接続ごとにスレッドを作る方式ではないため、数千のアイドル接続があってもスレッドを消費しません。
- パースされたリクエストは**ワーカースレッドプール**にディスパッチされ、クエリが実行されます。
- IndexとDocumentStoreは、それぞれの状態を同期します。検索は必要なデータを取る短い共有アクセスを行い、binlogイベントの適用は更新を調整してから新しい状態を公開します。
- 候補テキストは上限付きのチャンクで取り出します。BM25スコアリング、出現頻度の集計、テキストのポストフィルタを実行する前にDocumentStoreのロックを解放するため、時間のかかる処理がストアをロックし続けません。
- キャッシュ無効化は N-gram、フィルタ、テキスト変化に敏感な依存関係の逆引きインデックスを使います。定期的なLRU保守は、全エントリを1回の排他ロックで走査せず、上限付きの範囲から再開します。
- コネクション単位の**バックプレッシャー**（`api.tcp.max_write_queue_bytes`、デフォルト16 MiB）により、書き込みキューが上限を超えた低速クライアントを強制切断し、メモリ枯渇を防止します。
- アトミックカウンターが統計情報（クエリ数、キャッシュヒット率）に使用され、ホットパスでのロック競合を回避します。

::: info 用語補足
**バックプレッシャー**は、遅いクライアントに合わせてサーバー側の送信待ちデータが増え続けないように制限する仕組みです。上限を超えた接続を切ることで、1つの接続がプロセス全体のメモリを使い切ることを防ぎます。
:::

すべてのスレッドはシャットダウン時にjoinされます。デタッチされるスレッドはありません。

## 永続化

MygramDBは**スナップショットベースの永続化**を採用しており、WAL（Write-Ahead Log）は使用しません。

::: info 用語補足
**WAL** は変更を逐次ログに書く方式です。MygramDBはMySQLを正本として扱うため、独自WALではなく「定期ダンプ + MySQL binlogからの追いつき」で復旧します。
:::

<DocDiagram name="persistence-cycle" alt="メモリ上のインデックスと現在の GTID 位置をディスクのスナップショットファイルへ定期ダンプし、復旧時はそのダンプを読み込んでから保存済み GTID 以降の binlog を再適用する図" />

**仕組み：**

1. バックグラウンドスケジューラが定期的にインデックス、ドキュメントストア、現在のGTIDポジションをディスクにシリアライズします。
2. `dump.load_on_startup: true` の場合、起動時に `dump.dir/default_filename` を読み込みます。復元に成功すると、保存済み GTID からレプリケーションを再開します。この構成では `replication.start_from: snapshot` が必要です。
3. その GTID から現在の MySQL ポジションまでのイベントを自動で適用します。ダンプの検証に失敗した場合は MySQL から初期スナップショットを作成します。

スナップショット書き込みは**アトミックなファイル操作**（一時ファイルに書き込み後リネーム）を使用し、ダンプ中にプロセスが中断されてもファイル破損を防止します。

起動時にダンプ復元を試みない構成では、`replication.auto_initial_snapshot` を有効にして初期インデックスを自動作成するか、`SYNC <table>`（複数DB構成では `SYNC <database>.<table>`）を実行します。起動時のダンプ復元に失敗した場合は、`auto_initial_snapshot` が false でも MySQL から初期スナップショットを作成します。

::: warning MySQLバックアップの代替ではありません
MygramDBのスナップショットは検索インデックスを復旧するためのものです。MySQL本体のバックアップやポイントインタイムリカバリは、MySQL側で別途用意してください。
:::

## メモリレイアウト

<DocDiagram name="memory-layout" alt="テーブルごとに、インデックスが N-gram マップとポスティングリストを、ドキュメントストアが主キー、フィルタカラム、正規化テキストを保持し、共有キャッシュがクエリ結果と N-gram 逆引きインデックスを持つメモリ構成図" />

**サイジングの参考値。** 以下は公開している v1.10.0 のベンチマーク実測値です。110万件のWikipedia記事（英語100万件・日本語10万件、平均666文字）を`verify_text: all`で、32 GiB のコンテナ上で計測しています。実行条件の全体は[ベンチマーク](/ja/benchmarks)をご覧ください。

| コンポーネント | メモリ |
|--------------|--------|
| Index（N-gramマップ + ポスティングリスト） | 約152 MB |
| DocumentStore + テキストストア | 約1.78 GB |
| **RSS合計** | **約3.41 GB** |

現行サーバーは `verify_text: off` でも正規化テキストを保持します。ハイライトをクエリごとに指定できるためです。`verify_text` が制御するのは後段の照合であり、テキストの保存ではありません。容量見積もりについては[FAQ](/ja/faq#mygramdbに必要なメモリ量は)を参照してください。フィルタ値はインターン済みのカラム ID を小さなソート済みベクトルで持つため、ドキュメントと設定済みフィルタカラムの組ごとにカラム名の文字列とハッシュマップを持つ必要がありません。

上記ベンチマークでは、保存されたテキストとドキュメントデータがメモリの大部分を占めます。ポスティングリストのメモリ効率は圧縮戦略に依存します。疎なN-gramにはデルタエンコーディング、密なN-gramにはRoaringビットマップが使用されます。監視のたびに全テーブルをロックするのではなく、テーブルごとの値を上限付きスナップショットへ集約し、`INFO`、`/metrics`、Prometheusへ返します。適応的圧縮の詳細は[仕組み](/ja/docs/how-it-works#%E3%83%9B%E3%82%9A%E3%82%B9%E3%83%86%E3%82%A3%E3%83%B3%E3%82%AF%E3%82%99%E3%83%AA%E3%82%B9%E3%83%88%E5%9C%A7%E7%B8%AE)をご覧ください。

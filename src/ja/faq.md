# よくある質問

GTID、binlog、N-gram、BM25、Roaring Bitmapなどの用語は[用語集](/ja/docs/glossary)でも説明しています。初めて読む場合は、FAQとあわせて参照してください。

## MySQL FULLTEXTの問題

### MySQL FULLTEXTが遅いのはなぜですか？

MySQL FULLTEXT の応答時間は、クエリ、データ、ソート、バッファプールの状態、同時実行数によって変わります。検索経路は[アーキテクチャ比較](/ja/why)を参照してください。公開ベンチマークのバッファプールヒット率は 99.9989% であり、毎回のディスク読み込みで差が生じたわけではありません。

**解決策**: MygramDBは検索インデックスをメモリ上に保持します。現在のキャッシュ無効の実測値は[ベンチマーク](/ja/benchmarks)を参照してください。

### MySQL FULLTEXTが負荷時にタイムアウトします。どう対処すべきですか？

MygramDBを検索レプリカとして追加してください。同じデータセットでクエリキャッシュ無効のスループットを比較した結果は、[再現可能なベンチマーク](/ja/benchmarks)に掲載しています。

### アプリケーションを変更せずにMySQL FULLTEXTを高速化できますか？

MySQL への書き込み処理は変えずに導入できますが、MygramDB は独自の TCP/HTTP 検索 API を使います。アプリの検索経路を MygramDB に変更する必要があり、既存の MySQL FULLTEXT SQL が自動で高速化されるわけではありません。セットアップは[クイックスタート](/ja/)をご覧ください。

::: tip 変更が必要な部分
MySQLへの書き込み処理は変えずに済みます。ただし、検索リクエストの向き先はMygramDBのTCP APIまたはHTTP APIへ変更する必要があります。
:::

## 他の選択肢との比較

### Elasticsearchの代わりにMygramDBを使うべきですか？

詳しくは[比較ページ](/ja/comparison)をご覧ください。端的に言えば、データがRAMに収まりMySQL/MariaDBとのシンプルな連携が必要ならMygramDB。複数ノードにまたがる分散検索、ペタバイト規模のデータ、より高度な分析・集計機能が必要ならElasticsearch。

### MeilisearchやTypesenseとの違いは？

MeilisearchやTypesenseは、タイポ補正・ファセット検索・管理UIを備えた汎用検索エンジンです。MygramDBは異なる問題を解決します。MySQLからbinlogで直接同期するインメモリ検索レプリカです。データが既にMySQLにあり、ETLパイプラインなしで高速な全文検索が必要な場合はMygramDBの方がシンプルです。独立した検索プラットフォームとして独自のデータ取り込みが必要な場合は、MeilisearchやTypesenseが適しています。

### RediSearchとの違いは？

どちらもインメモリの全文検索エンジンですが、アーキテクチャが根本的に異なります。

| | MygramDB | RediSearch |
|---|---|---|
| **データ同期** | MySQL/MariaDB binlogで自動同期 | プッシュ型（FT.ADD）— ETLは自前で構築 |
| **依存** | MySQLまたはMariaDB | Redis（Redis Stack） |
| **デプロイ** | 単一バイナリ | Redisモジュール |
| **機能** | N-gram検索＋BM25スコア、ハイライト、ファジー検索、ファセット集計、シノニム展開 | ファジー検索、ハイライト、集計、地理 |
| **ライセンス** | MIT | RSALv2 / SSPL（商用制限あり） |

最大の違いはデータフローです。RediSearchはドキュメントをRedisにプッシュする必要があり、MySQLとRedis間のETLパイプラインが必要です。MygramDBはMySQL/MariaDBのbinlogを直接読み取り、自動で同期を維持します。データがMySQL/MariaDBにあり、同期パイプラインを構築せずに検索したい場合はMygramDBの方がシンプルです。既にRedisを運用しており、地理検索やより豊富な集計モデルが必要な場合は、RediSearchの統合コストに見合う可能性があります。

## 機能と制約

### MygramDBに必要なメモリ量は？

[公開した v1.10.0 のベンチマーク](/ja/benchmarks)では、`verify_text: all` で**100万ドキュメントあたり約{{ VERIFY_ALL_PER_MILLION_GB }}GB**の常駐メモリを計測しました。インデックス、保存テキスト、プロセスのオーバーヘッドを含みます。同種のドキュメントが1000万件なら、単純な比例計算で余裕分を除き約{{ PLANNING_10M_ALL_GB }}GBです。現行版は `verify_text: off` でも、クエリ時にハイライトを指定できるよう正規化テキストを保持します。この設定は後段の照合を制御するため、インデックスだけの容量見積もりには使えません。実データで測定し、余裕分を確保してください。

::: warning メモリ不足時の挙動
MygramDBはインメモリ検索エンジンです。データセットが利用可能RAMを超えると、OSやコンテナ基盤のOOMによってプロセスが終了する可能性があります。本番ではダンプ領域とは別に、インデックス用RAMと余裕分を確保してください。
:::

### MygramDBは日本語に対応していますか？

はい。ICUベースのUnicode正規化とN-gramトークナイズを使用。日本語・中国語・韓国語は追加プラグインなしでそのまま動作します。

### ファジー検索（タイポ補正）には対応していますか？

はい。クエリに `FUZZY`（または `FUZZY 2`）を追加すると、Levenshtein 編集距離 1 または 2 以内の語句にマッチします。短い語や CJK/ASCII 混在語も含め、同じクエリの通常検索結果はすべて残ります。詳しくは[クエリガイド — ファジー検索](/ja/docs/queries#%E3%83%95%E3%82%A1%E3%82%B7%E3%82%99%E3%83%BC%E6%A4%9C%E7%B4%A2)を参照してください。

### 検索結果のハイライトには対応していますか？

はい。`HIGHLIGHT` 句を追加すると、設定可能なタグ（`TAG`）、フラグメント長（`SNIPPET_LEN`）、フラグメント数（`MAX_FRAGMENTS`）でスニペットが返却されます。`memory.verify_text: "off"` でも、サーバーはハイライト用の正規化テキストを保持します。詳しくは[クエリガイド — ハイライト](/ja/docs/queries#ハイライト)を参照してください。

### 関連度順のランキングには対応していますか？

はい。`SORT _score DESC` を使うとBM25関連度スコアで並び替えられます。IDF／TFはクエリ時に計算され、`k1` と `b` は `bm25.k1`（デフォルト `1.2`）／`bm25.b`（デフォルト `0.75`）で調整できます。`bm25.enable: true` を設定してください。スコア計算に使う正規化テキストは `memory.verify_text` の設定にかかわらず保持されます。

### 水平スケールは可能ですか？

組み込みのスケール機能はありません。同じデータを持つフルレプリカをロードバランサーの背後に配置すれば、読み取り容量と可用性は高められますが、各インスタンスはインデックス全体を保持します。1ノードの RAM を超えるデータセットでは、元データを別々にインデックスするテーブルやインスタンスへ分割し、アプリ側でクエリを振り分けたり結果を統合したりする必要があります。

必要な容量はドキュメントの長さやフィルタによって変わります。公開ベンチマークでは `verify_text: all` で100万件あたり約3.1GBを使用しました。ノードのサイズは実データで測定し、インデックス構築や保守処理の余裕も確保してください。

### 複数テーブルを横断検索できますか？

できません。各クエリは単一テーブルを対象とします：`SEARCH articles hello world`。MygramDBは複数テーブルの設定に対応していますが、各テーブルは独立したインデックスとドキュメントストアを持ちます。クロステーブル検索はアプリケーション層で個別クエリとして処理してください。

### 1つのMygramDBインスタンスで複数のMySQLデータベースをインデックスできますか？

はい（v1.7.0以降）。各テーブルは `<database>.<table>` の有効識別子を持ちます。設定済みテーブルが1つのDBにだけ属する場合、`articles` のような修飾なしの名前も引き続き使えます。設定が2つ以上のDBにまたがる場合は、`SEARCH app_db.articles mysql` や `POST /tables/app_db.articles/search` のように修飾が必要です。

### MygramDBはPostgreSQLに対応していますか？

非対応です。MygramDBはMySQL固有のバイナリログレプリケーションプロトコルに依存しています。PostgreSQLは異なる仕組み（WALベースのロジカルレプリケーション）を使用しています。現時点でPostgreSQL対応の予定はありません。

### MariaDBで動作しますか？

はい。MygramDB は MariaDB 10.11+/11.x/12.x に対応し、MariaDB ネイティブの GTID 形式（`domain-server-sequence`）でレプリケーションします。機能プローブでサーバー種別を判定するため、MySQL 8.4/9.x と MariaDB で同じ `mysql` セクションを使用できます。E2E テストでは MariaDB 10.11、11.8、12.3 を検証しています。

## インデックスと検索

### なぜ形態素解析ではなくN-gramですか？

N-gramトークナイズは言語に依存しません。形態素解析器（MeCab、kuromoji、jieba）は辞書・言語判定・バージョン管理が必要です。N-gramは英語・日本語・中国語・韓国語・多言語混在コンテンツで一律に動作します。

MygramDBは、ASCII/英数字とCJKの漢字のどちらにもデフォルトでバイグラム（サイズ2）を使います。CJKの漢字だけ別の長さにするには `kanji_ngram_size` を設定します。どちらもテーブル単位で設定でき、`ngram_size` 省略時のデフォルトは `2` です。

### Roaring Bitmapはどう使われていますか？

転置リストは密度に応じたハイブリッドストレージ戦略を採用しています：

- **疎な転置リスト**（全ドキュメントの18%未満）: デルタエンコーディング配列。DocIDを前の値との差分として固定幅で保存。
- **密な転置リスト**（18%以上）: CRoaringによるRoaring Bitmap。65,536 ID単位のチャンクごとに最適なコンテナタイプ（配列・ビットマップ・ランレングス）を自動選択。

閾値は`roaring_threshold`で設定可能。フォーマット間の振動を防ぐヒステリシス係数（0.5倍）があります。

### 「SIMD高速化」とは具体的に何ですか？

MygramDBは[CRoaring](https://github.com/RoaringBitmap/CRoaring)をリンクしており、CRoaringがビットマップ演算（AND、OR、カーディナリティ）で内部的にSIMD命令を使用します。x86-64ではAVX2、ARMではNEONを利用。MygramDB自体にカスタムSIMDコードはなく、高速化はビットマップライブラリ由来です。

### ポスティングリストはどうエンコードされますか？

疎な語には Delta エンコーディングのリスト、密な語には Roaring ビットマップを使います。メモリ使用量は DocID の分布によって変わります。

1. **デルタエンコーディング**: 単調増加する DocID を差分に変換します。例：`[1000, 1002, 1005]` → `[1000, 2, 3]`。現行の表現では各差分を `uint32_t` で保持します。
2. **Roaring Bitmap圧縮**: 密な転置リストはRoaringのコンテナ最適化を使用。連続範囲にはランレングスエンコーディング、散在する密な領域にはビットマップコンテナ。

データセットを問わず一定の圧縮率になるわけではありません。実データでインデックスメモリを測定し、[公開ベンチマークの内訳](/ja/docs/architecture#%E3%83%A1%E3%83%A2%E3%83%AA%E3%83%AC%E3%82%A4%E3%82%A2%E3%82%A6%E3%83%88)も参照してください。

## レプリケーションとデータ同期

### MySQLのbinlogパーサーは自前実装ですか？

はい。MygramDBはMySQL C API（`mysql_binlog_open()`）を直接使用する独自のC++ binlogパーサーを含んでいます。ROW形式のイベント（WRITE_ROWS、UPDATE_ROWS、DELETE_ROWS）およびDDLイベント（TRUNCATE、ALTER TABLE）をパースします。[mysql-event-stream](https://github.com/libraz/mysql-event-stream)は後から独立したCDCライブラリとして切り出されたもので、Node.jsとPythonバインディングを備えています。

### レプリケーションの速度は？INSERTから検索可能になるまで？

遅延はソースのトランザクション、ネットワーク、イベントキュー、インデックス更新によって変わります。[HTTP API の `/metrics`](/ja/docs/http-api#get-metrics) にある `mygramdb_replication_last_applied_unixtime` と `mygramdb_replication_seconds_since_last_applied` を MySQL の書き込み状況と併せて監視してください。`api.admin_token` を設定している場合、Prometheus がこれらのメトリクスを取得するには有効な Bearer トークンが必要です。ソースがアイドルなら、最後に適用した時刻が古くても遅延しているとは限りません。

### MySQLフェイルオーバー時の挙動は？

MygramDB は接続断を検知すると、設定済みの接続先へ再接続します。再接続時：

1. 現在のGTIDポジションを保持
2. 接続先のサーバー UUID を確認し、異なるソースは拒否
3. 同じソースなら保存済み GTID から binlog レプリケーションを再開

`mysql.host` と `mysql.port` は `SET` で変更できません。接続先を移す場合は対象ソースを確認し、設定ファイルを変更して再起動してください。再接続中は readiness とレプリケーション遅延を監視してください。

### ALTER TABLEはどう処理されますか？

MygramDB は binlog 経由で DDL イベントを検知します。`TRUNCATE TABLE` は対象インデックスをクリアします。設定済みテーブルの削除やリネーム、別のテーブルから設定済みテーブル名へのリネーム、設定済みの主キー・テキストソース・フィルタカラムへの互換性のない変更では、GTID を進める前にレプリケーションを停止します。設定済みテーブルが `DROP TABLE` された場合、既存のインデックスは停止中も残りますが、最新ではありません。スキーマまたは設定を修正してから、対象テーブルを `SYNC` で再構築してください。

### インデックスからの削除はどう処理されますか？

即時削除です。binlog経由でDELETEイベントが到着すると、ドキュメントのN-gramが転置リストから除去され、ドキュメントストアからも削除されます。トゥームストーンや遅延削除はありません。削除されたドキュメントを参照するキャッシュエントリは無効化されます。

## 障害復旧と永続化

### クラッシュ時の復旧は？WALはありますか？

WALはありません。MygramDBはスナップショットベースの永続化を採用しています：

1. 定期または手動の `DUMP SAVE` で、GTID ポジションとともにインデックスを保存します。定期ダンプのファイル名には日時が入ります。
2. `dump.load_on_startup: true` の場合、起動時に最新の日時付きダンプではなく `dump.dir/default_filename` を読み込みます。成功するとダンプの GTID からレプリケーションを再開します。この構成では `replication.start_from: snapshot` を設定してください。

起動時ダンプが見つからないか検証に失敗した場合は、MySQL から初期スナップショットを作成します。MySQL は引き続き正本です。MySQL のバックアップと binlog は別に保存してください。復元時の確認事項は[ダンプの保存と復旧](/ja/docs/snapshot)を参照してください。

ダンプ設定：
- `dump.interval_sec`: 自動保存間隔（0 = 無効、本番推奨: 7200）
- `dump.retain`: 保持するダンプ数（デフォルト: 3）

### メモリがハードリミットに達するとどうなりますか？

MygramDB はヘルスチェックエンドポイントでメモリ使用量を監視しますが、ハードリミットに達してもクエリの拒否やレプリケーションの停止は行いません。インデックスが利用可能な RAM を超えると、OS の OOM killer によってプロセスが終了する可能性があります。全データセットを載せる RAM に余裕を加えてください。`verify_text: all` の実測参考値は 100 万ドキュメントあたり約{{ VERIFY_ALL_PER_MILLION_GB }}GB です。`/health/detail` や Prometheus メトリクスでメモリ使用量を監視してください。

## プロトコルとセキュリティ

### クエリプロトコルは何ですか？

TCP上のカスタムテキストプロトコル（デフォルトポート11016）で、Memcachedに似ています。REST/JSONのHTTP APIは別ポート（デフォルト8080、起動時はデフォルト無効）で提供されます。

TCP例：
```mygram
SEARCH articles golang SORT created_at DESC LIMIT 10\r\n
```

HTTP例：
```bash
curl -X POST http://localhost:8080/tables/articles/search \
  -H "Content-Type: application/json" \
  -d '{"q": "golang", "sort": {"column": "created_at", "order": "DESC"}, "limit": 10}'
```

複数DB構成では `/tables/app_db.articles/search` のように修飾します。SQLではありません。検索、カウント、ファセット、ID取得、管理コマンドに絞った最小限のプロトコルです。

### TLSや認証はありますか？

MygramDBにはネイティブTLSがありません。必要に応じてリバースプロキシやロードバランサーでTLSを終端してください。MySQLレプリケーション接続はSSL/TLSをサポートしています。

`api.admin_token` を設定した場合、TCP の管理コマンドには接続ごとに `AUTH <token>` が必要です。HTTP の `GET /config`、`GET /replication/status`、`POST /optimize` にはリクエストごとに `Authorization: Bearer <token>` を渡します。検索エンドポイントはリスナーのバインドアドレスと `NETWORK_ALLOW_CIDRS` で制御します。プライベートネットワーク内か、リバースプロキシまたはファイアウォールの背後で運用してください。

## デプロイと監視

### Kubernetesで動作しますか？

必要な要素は揃っています。ヘルスチェックエンドポイントが組み込まれています：

- `GET /health/live` — Livenessプローブ（プロセス稼働中なら200）
- `GET /health/ready` — Readinessプローブ（DUMP LOAD中、テーブル同期中、またはレプリケーション利用不可なら503、準備完了で200）
- `GET /health/detail` — アップタイム、インデックス統計、メモリを含む詳細ステータス。`api.admin_token` 設定時、レプリケーションの詳細には Bearer トークンが必要です

Prometheusメトリクスは`GET /metrics`で取得できます。Dockerイメージは非rootユーザー（UID 1000）で実行されます。Kubernetesで運用する場合は、永続ボリューム、メモリ制限、Readiness/Livenessプローブ、MySQLへのネットワーク経路を環境に合わせて設定してください。

### どのようなメトリクスが取得できますか？

`GET /metrics`でPrometheus形式のメトリクスを提供：

- コマンド件数（`mygramdb_command_total`）。カウンターから毎秒の処理件数を計算可能
- テーブルごとのインデックス文書数と語数
- キャッシュヒット率、メモリ、エビクション件数
- プロセス RSS と集計されたインデックスメモリ
- レプリケーション状態、処理イベント数、最終適用イベントからの経過秒数
- 接続中のクライアント数と拒否リクエスト件数

### 「単一バイナリ」と言いつつMySQLが必要 — それは本当にシンプルですか？

MygramDBは「既存のMySQLに検索レプリカを追加する」作業を小さくする設計です。データベースを置き換えるのではなく、MySQLの横に配置し、GTID/binlog設定、レプリケーションユーザー、対象テーブル、ネットワーク許可範囲を設定します。スキーマ変更や検索用ETLパイプラインは基本的に不要ですが、検索リクエストの向き先はMygramDBのTCP APIまたはHTTP APIへ切り替える必要があります。

## ベンチマーク

### ベンチマークのハードウェア環境は？

110万件のWikipedia記事（英語100万件＋日本語10万件）でテスト。MySQLは8.4.11をDockerで実行、MygramDBは`verify_text: all`（ポストフィルタ有効）でクエリキャッシュ無効。Apple M5 Maxホスト（18コア / 128 GiB）でDocker Desktopに32 GiBを割り当て、コンテナからは31.29 GiBが利用可能な状態で実行しました。各クエリはウォームアップ5回のあと200回計測しています。別のハードウェアやメモリ上限では絶対レイテンシが変わります。

### ベンチマークでMySQL側の設定はチューニングしましたか？

しています。`innodb_buffer_pool_size`を8.0 GiBに設定し、FULLTEXTの作業セットが収まる状態で計測しました。実行中のバッファプールヒット率は99.9989%、ディスク読み込みは7,809回です。[ベンチマーク](/ja/benchmarks)の数値は、十分なメモリを与えたウォーム状態のFULLTEXTとの比較です。

### MySQLはコールドキャッシュとウォームキャッシュのどちらでテストしましたか？

ウォームです。実行中のバッファプールヒット率が99.9989%なので、MySQL FULLTEXTはほぼメモリから読んでいます。同じ計測でMygramDB側のクエリキャッシュは無効にしているため、MygramDBの数値はキャッシュヒットではなく検索エンジンの実処理を表します。どちらの設定も[ベンチマーク](/ja/benchmarks)に記載しています。

### なぜElasticsearchとの実測比較がないのですか？

Elasticsearchの性能はクラスタ構成、シャード設計、マッピング、JVM設定で大きく変わります。単純なシングルノード比較では用途差を説明しにくいため、このサイトでは[比較ページ](/ja/comparison)で定性的な使い分けを示しています。

## プロジェクト

### なぜRustではなくC++ですか？

C++を選んだ主な理由は、メモリレイアウトを細かく制御したかったためです。転置リスト操作、ビットマップ演算、デルタエンコーディングでは、データをどのようにメモリ上へ配置するかが性能とメモリ効率に直結します。実装ではRAII、`unique_ptr`による所有権管理、例外の代わりの`Expected<T, Error>`を使い、C++で起きやすい問題を抑えています。Rustにも強い利点がありますが、MygramDBでは低レベルなメモリ制御と既存C/C++ライブラリ連携を優先しています。

### プロジェクトの成熟度は？

開発は2025年11月に開始しました。高トラフィックなサービスで本番利用実績があります（詳細はNDAにより非公開）。

### MySQL FULLTEXTからMygramDBへの移行方法は？

MySQLはそのまま維持し、MygramDBを横に立てて、検索クエリだけルーティングします。既存行は初回 `SYNC` で読み込み、その後の変更はbinlogで追従します。[クイックスタート](/ja/)または[比較 — 移行方法](/ja/comparison#移行方法)をご覧ください。

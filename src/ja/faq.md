# よくある質問

GTID、binlog、N-gram、BM25、Roaring ビットマップなどの用語は[用語集](/ja/docs/glossary)でも説明しています。初めて読む場合は、FAQ とあわせて参照してください。

## MySQL FULLTEXT の問題

### MySQL FULLTEXT が遅いのはなぜですか？

MySQL FULLTEXT の応答時間は、クエリ、データ、ソート、バッファプールの状態、同時実行数によって変わります。検索経路は[アーキテクチャ比較](/ja/why)を参照してください。公開ベンチマークのバッファプールヒット率は 99.9989% でした。測定された差は、クエリごとのディスク読み込みでは説明できません。

**解決策**: MygramDB は検索インデックスをメモリ上に保持します。現在のキャッシュ無効の実測値は[ベンチマーク](/ja/benchmarks)を参照してください。

### MySQL FULLTEXT が負荷時にタイムアウトします。どう対処すべきですか？

MygramDB を検索レプリカとして追加してください。同じデータセットでクエリキャッシュ無効のスループットを比較した結果は、[再現可能なベンチマーク](/ja/benchmarks)に掲載しています。

### アプリケーションを変更せずに MySQL FULLTEXT を高速化できますか？

MySQL への書き込み処理は変えずに導入できますが、MygramDB は独自の TCP/HTTP 検索 API を使います。アプリの検索経路を MygramDB に変更する必要があり、既存の MySQL FULLTEXT SQL が自動で高速化されるわけではありません。セットアップは[クイックスタート](/ja/)をご覧ください。

## 他の選択肢との比較

### Elasticsearch の代わりに MygramDB を使うべきですか？

詳しくは[比較ページ](/ja/comparison)をご覧ください。端的には、データが RAM に収まり、MySQL/MariaDB とシンプルに連携したいなら MygramDB が向いています。複数ノードにまたがる分散検索、ペタバイト規模のデータ、高度な分析や集計が必要なら Elasticsearch が向いています。

### Meilisearch や Typesense との違いは？

Meilisearch や Typesense には、それぞれ異なる機能とデータ取り込み方法があります。MygramDB は MySQL または MariaDB の binlog を読み、検索インデックスを更新します。検索要件やデータの流れに加え、各製品の最新のデプロイ要件とライセンスを確認して選んでください。

### RediSearch との違いは？

MygramDB は MySQL または MariaDB の binlog を読み、検索インデックスを更新します。他製品と比較する場合は、データ取り込み方法、機能、デプロイ要件、ライセンスについて各製品の最新ドキュメントを確認してください。

## 機能と制約

### MygramDB に必要なメモリ量は？

[公開した v1.10.0 のベンチマーク](/ja/benchmarks)では、`verify_text: all` で **100万ドキュメントあたり約{{ VERIFY_ALL_PER_MILLION_GB }}GB** の常駐メモリを計測しました。インデックス、保存テキスト、プロセスのオーバーヘッドを含みます。同種のドキュメントが 1000万件なら、単純な比例計算で余裕分を除き約{{ PLANNING_10M_ALL_GB }}GB です。現行版は `verify_text: off` でも、クエリ時にハイライトを指定できるよう正規化テキストを保持します。この設定は後段の照合を制御するため、インデックスだけの容量見積もりには使えません。実データで測定し、余裕分を確保してください。

::: warning メモリ不足時の挙動
MygramDB はインメモリ検索エンジンです。データセットが利用可能 RAM を超えると、OS やコンテナ基盤の OOM によってプロセスが終了する可能性があります。本番ではダンプ領域とは別に、インデックス用 RAM と余裕分を確保してください。
:::

### MygramDB は日本語に対応していますか？

はい。テキストは ICU ベースの NFKC 正規化を通したあと、言語に依存しない N-gram トークナイザーで分割します。3 バイトの UTF-8（日本語・中国語・韓国語などの漢字圏の文字）も、4 バイトの UTF-8（絵文字や補助面の文字）も、そのまま扱えます。言語別のプラグイン、辞書、形態素解析器の設定は不要です。

### あいまい検索（タイポ補正）には対応していますか？

はい。クエリに `FUZZY`（または `FUZZY 2`）を追加すると、Levenshtein 編集距離 1 または 2 以内の語句にマッチします。短い語や CJK/ASCII 混在語も含め、同じクエリの通常検索結果はすべて残ります。詳しくは[クエリガイド — あいまい検索](/ja/docs/queries#あいまい検索)を参照してください。

### 検索結果のハイライトには対応していますか？

はい。`HIGHLIGHT` 句を追加すると、設定可能なタグ（`TAG`）、フラグメント長（`SNIPPET_LEN`）、フラグメント数（`MAX_FRAGMENTS`）でスニペットが返却されます。`memory.verify_text: "off"` でも、サーバーはハイライト用の正規化テキストを保持します。詳しくは[クエリガイド — ハイライト](/ja/docs/queries#ハイライト)を参照してください。

### 関連度順のランキングには対応していますか？

はい。`SORT _score DESC` を使うと BM25 関連度スコアで並び替えられます。IDF／TF はクエリ時に計算され、`k1` と `b` は `bm25.k1`（デフォルト `1.2`）／`bm25.b`（デフォルト `0.75`）で調整できます。`bm25.enable: true` を設定してください。スコア計算に使う正規化テキストは `memory.verify_text` の設定にかかわらず保持されます。

### 水平スケールは可能ですか？

MygramDB はインデックスをノード間で分割しません。同じデータを持つフルレプリカをロードバランサーの背後に配置すれば読み取り容量を増やせますが、各インスタンスはインデックス全体を保持し、それぞれ異なる `REPLICATION_SERVER_ID` を含むレプリケーション設定が必要です。ready になったインスタンスにだけトラフィックを送ってください。1 ノードの RAM に収まらない場合は、元データを別々にインデックスするテーブルやインスタンスへ分け、アプリ側でクエリを振り分けたり結果を統合したりします。

必要な容量はドキュメントの長さやフィルタによって変わります。公開ベンチマークでは `verify_text: all` で 100万件あたり約 3.1GB を使用しました。ノードのサイズは実データで測定し、インデックス構築や保守処理の余裕も確保してください。

### 複数テーブルを横断検索できますか？

できません。1回のクエリで対象にできるのは 1つのテーブルです（例: `SEARCH articles hello world`）。MygramDB は複数テーブルの設定に対応していますが、各テーブルは独立したインデックスとドキュメントストアを持ちます。クロステーブル検索はアプリケーション層で個別クエリとして処理してください。

### 1つの MygramDB インスタンスで複数の MySQL データベースをインデックスできますか？

はい（v1.7.0 以降）。各テーブルは `<database>.<table>` のテーブル識別子を持ちます。設定済みテーブルが 1つの DB にだけ属する場合、`articles` のような修飾なしの名前も引き続き使えます。設定が 2つ以上の DB にまたがる場合は、`SEARCH app_db.articles mysql` や `POST /tables/app_db.articles/search` のように修飾が必要です。

### MygramDB は PostgreSQL に対応していますか？

非対応です。MygramDB は MySQL 固有のバイナリログレプリケーションプロトコルに依存しています。PostgreSQL は異なる仕組み（WAL ベースのロジカルレプリケーション）を使用しています。現時点で PostgreSQL 対応の予定はありません。

### MariaDB で動作しますか？

はい。MygramDB は MariaDB 10.11+/11.x/12.x に対応し、MariaDB ネイティブの GTID 形式（`domain-server-sequence`）でレプリケーションします。機能プローブでサーバー種別を判定するため、MySQL 8.4/9.7/26.x と MariaDB で同じ `mysql` セクションを使用できます。E2E テストでは MariaDB 10.11、11.4、11.8、12.3 を検証しています。

## インデックスと検索

### なぜ形態素解析ではなく N-gram ですか？

N-gram トークナイズは言語に依存しません。形態素解析器（MeCab、kuromoji、jieba）は辞書・言語判定・バージョン管理が必要です。N-gram は英語・日本語・中国語・韓国語・多言語混在コンテンツで一律に動作します。

MygramDB は、ASCII/英数字と CJK の漢字のどちらにもデフォルトでバイグラム（サイズ 2）を使います。CJK の漢字だけ別の長さにするには `kanji_ngram_size` を設定します。どちらもテーブル単位で設定でき、`ngram_size` 省略時のデフォルトは `2` です。

### Roaring Bitmap はどう使われていますか？

ポスティングリストはデルタエンコーディングまたは Roaring ビットマップで保持します。`OPTIMIZE` は密度に応じて形式を選び、挿入時にはリストの件数に応じて変換します。

| ポスティングリスト | 条件 | 形式 |
| --- | --- | --- |
| 疎 | `OPTIMIZE` 後の密度が通常 18% 未満 | デルタエンコードした配列。DocID を前の値との差分として、固定幅で保存します。 |
| 密 | `OPTIMIZE` 後の密度が通常 18% 以上、または挿入後に 4,096件を超える | CRoaring による Roaring ビットマップ。65,536 ID 単位のチャンクごとに、コンテナタイプ（配列・ビットマップ・ランレングス）を自動で選びます。 |

密度閾値は `roaring_threshold` で設定でき、`OPTIMIZE` では 0.5倍のヒステリシスを使います。デルタ形式は挿入で 4,096件を超えると密度に関係なく Roaring へ変換されます。Roaring から戻るのは、件数が 4,096 以下かつ密度が閾値の半分（デフォルト 9%）未満の場合です。

### 「SIMD 高速化」とは具体的に何ですか？

MygramDB は [CRoaring](https://github.com/RoaringBitmap/CRoaring) をリンクしており、CRoaring がビットマップ演算（AND、OR、カーディナリティ）で内部的に SIMD 命令を使用します。x86-64 では AVX2、ARM では NEON を使います。MygramDB 自体にカスタム SIMD コードはなく、高速化はビットマップライブラリによるものです。

### ポスティングリストはどうエンコードされますか？

`OPTIMIZE` は疎な語にはデルタエンコーディング、密な語には Roaring ビットマップを選びます。挿入で 4,096件を超えたリストも Roaring へ変換されます。メモリ使用量は DocID の分布によって変わります。

1. **デルタエンコーディング**: 単調増加する DocID を差分に変換します。例：`[1000, 1002, 1005]` → `[1000, 2, 3]`。現行の表現では各差分を `uint32_t` で保持します。
2. **Roaring ビットマップ圧縮**: 密なポスティングリストには Roaring のコンテナ最適化を使います。連続する範囲にはランレングスエンコーディング、散在する密な領域にはビットマップコンテナを使います。

データセットを問わず一定の圧縮率になるわけではありません。実データでインデックスメモリを測定し、[公開ベンチマークの内訳](/ja/docs/architecture#%E3%83%A1%E3%83%A2%E3%83%AA%E3%83%AC%E3%82%A4%E3%82%A2%E3%82%A6%E3%83%88)も参照してください。

## レプリケーションとデータ同期

### binlog のデコードは何が担っていますか？

MygramDB は MySQL C API（`mysql_binlog_open()`）で生の binlog ストリームを受け取り、別リポジトリの C++17 ライブラリ [libmybinlog](https://github.com/libraz/libmybinlog) でデコードします。libmybinlog は MySQL と MariaDB のワイヤ形式の規則（フレーミング、チェックサム、`TABLE_MAP`、GTID、`QUERY` イベント、行イベント）を受け持ちます。MygramDB はデコードされた行イベントをインデックスへ適用し、`TRUNCATE` や `ALTER TABLE` など必要な DDL を処理します。Node.js と Python のバインディングを持つ CDC ライブラリ [mysql-event-stream](https://github.com/libraz/mysql-event-stream) も、同じ libmybinlog でデコードしています。処理の流れの全体は [binlog デコード](/ja/docs/binlog-decoding) を参照してください。

### レプリケーションの速度は？INSERT から検索可能になるまで？

レプリケーション遅延は、ソースのトランザクション、ネットワーク、イベントキュー、インデックス更新によって変わります。[HTTP API の `/metrics`](/ja/docs/http-api#get-metrics) にある `mygramdb_replication_last_applied_unixtime` と `mygramdb_replication_seconds_since_last_applied` を MySQL の書き込み状況と併せて監視してください。`api.admin_token` を設定している場合、Prometheus がこれらのメトリクスを取得するには有効な Bearer トークンが必要です。ソースがアイドルなら、最後に適用した時刻が古くても遅延しているとは限りません。

### MySQL フェイルオーバー時の挙動は？

MygramDB は接続断を検知すると、設定済みの接続先へ再接続します。再接続時は次の順に動作します。

1. 現在の GTID 位置を保持する
2. 接続先のサーバー UUID を確認し、異なるソースは拒否する
3. 同じソースなら、保存済みの GTID から binlog レプリケーションを再開する

`mysql.host` と `mysql.port` は `SET` で変更できません。接続先を移す場合は対象ソースを確認し、設定ファイルを変更して再起動してください。再接続中は、ノードが ready になるかどうかとレプリケーション遅延を監視してください。

### ALTER TABLE はどう処理されますか？

MygramDB は binlog 経由で DDL イベントを検証します。`CREATE INDEX` と `DROP INDEX` も検証対象です。`TRUNCATE TABLE` は対象インデックスをクリアします。設定済みテーブルの削除やリネーム、別のテーブルから設定済みテーブル名へのリネーム、設定済みの主キー・テキストソース・フィルタカラムへの互換性のない変更では、GTID を進める前にレプリケーションを停止します。設定した主キーカラムが単独の `PRIMARY KEY` または `UNIQUE` インデックスでなくなった場合も、検証に失敗してレプリケーションが停止します。設定済みテーブルが `DROP TABLE` された場合、既存のインデックスは停止中も残りますが、最新ではありません。スキーマまたは設定を修正してから、対象テーブルを `SYNC` で再構築してください。

### インデックスからの削除はどう処理されますか？

即時削除です。binlog 経由で DELETE イベントが到着すると、ドキュメントの N-gram がポスティングリストから取り除かれ、ドキュメントストアからも削除されます。トゥームストーンや遅延削除はありません。削除されたドキュメントを参照するキャッシュエントリは無効化されます。

## 障害復旧と永続化

### クラッシュ時の復旧は？WAL はありますか？

WAL はありません。MygramDB はダンプによる永続化を採用しています。

1. 定期または手動の `DUMP SAVE` で、GTID 位置とともにインデックスを保存します。定期ダンプのファイル名には日時が入ります。
2. `dump.load_on_startup: true` の場合、起動時に最新の日時付きダンプではなく `dump.dir/default_filename` を読み込みます。成功するとダンプの GTID からレプリケーションを再開します。この構成では `replication.start_from: snapshot` を設定してください。

起動時ダンプが見つからないか検証に失敗した場合は、MySQL から初期スナップショットを作成します。MySQL は引き続き正本です。MySQL のバックアップと binlog は別に保存してください。復元時の確認事項は[ダンプの保存と復旧](/ja/docs/snapshot)を参照してください。

ダンプを復元したあと、MySQL の現在位置まで追いつけない場合は、復元したインデックスで検索を提供し続けますが、レプリケーションは停止し、readiness は `not_ready` になります。レプリケーションエラーとソースの GTID/binlog を確認し、[ダンプの保存と復旧](/ja/docs/snapshot)に沿って復旧または再構築してください。

ダンプの設定は次のとおりです。

| 設定 | デフォルト | 説明 |
| --- | --- | --- |
| `dump.interval_sec` | `0`（無効） | 自動保存の間隔（秒）。本番では 7200 を推奨します。 |
| `dump.retain` | `3` | 保持するダンプの数。 |

### メモリがハードリミットに達するとどうなりますか？

MygramDB はヘルスチェックエンドポイントでメモリ使用量を監視しますが、ハードリミットに達してもクエリの拒否やレプリケーションの停止は行いません。インデックスが利用可能な RAM を超えると、OS の OOM killer によってプロセスが終了する可能性があります。全データセットを載せる RAM に余裕を加えてください。`verify_text: all` の実測参考値は 100 万ドキュメントあたり約{{ VERIFY_ALL_PER_MILLION_GB }}GB です。`/health/detail` や Prometheus メトリクスでメモリ使用量を監視してください。

## プロトコルとセキュリティ

### クエリプロトコルは何ですか？

TCP 上のカスタムテキストプロトコル（デフォルトポート 11016）で、Memcached に似ています。REST/JSON の HTTP API は別ポート（デフォルト 8080、起動時はデフォルト無効）で提供されます。

TCP の例:

```mygram
SEARCH articles golang SORT created_at DESC LIMIT 10\r\n
```

HTTP の例:

```bash
curl -X POST http://localhost:8080/tables/articles/search \
  -H "Content-Type: application/json" \
  -d '{"q": "golang", "sort": {"column": "created_at", "order": "DESC"}, "limit": 10}'
```

複数 DB 構成では `/tables/app_db.articles/search` のように修飾します。SQL ではありません。検索、カウント、ファセット、ID 取得、管理コマンドに絞った最小限のプロトコルです。

### TLS や認証はありますか？

MygramDB にはネイティブ TLS がありません。必要に応じてリバースプロキシやロードバランサーで TLS を終端してください。MySQL レプリケーション接続は SSL/TLS をサポートしています。

`api.admin_token` を設定した場合、TCP の管理コマンドには接続ごとに `AUTH <token>` が必要です。HTTP の `GET /config`、`GET /replication/status`、`POST /optimize` にはリクエストごとに `Authorization: Bearer <token>` を渡します。認証していない場合、TCP の `INFO` には `# Replication` セクションが含まれず、`/metrics` には `mygramdb_replication_` のメトリクスが含まれません。検索エンドポイントはリスナーのバインドアドレスと `NETWORK_ALLOW_CIDRS` で制御します。プライベートネットワーク内か、リバースプロキシまたはファイアウォールの背後で運用してください。

## デプロイと監視

### Kubernetes で動作しますか？

はい。Kubernetes 向けのヘルスチェックとメトリクスを提供します。ダンプ用ストレージ、メモリ制限、プローブ、MySQL へのネットワーク経路は、環境に合わせて設定してください。

| エンドポイント | 用途 | 応答 |
| --- | --- | --- |
| `GET /health/live` | Liveness プローブ | プロセスが稼働中なら 200 |
| `GET /health/ready` | Readiness プローブ | `DUMP LOAD` 中、テーブル同期中、レプリケーションが利用できない場合、またはダンプ復元後の追いつきに失敗した場合は 503。準備完了なら 200 |
| `GET /health/detail` | 詳細ステータス | アップタイム、インデックス統計、メモリ。`api.admin_token` を設定している場合、レプリケーションの詳細には Bearer トークンが必要です |

Prometheus メトリクスは `GET /metrics` で取得できます。Docker イメージは非 root ユーザー（UID 1000）で実行されます。

### どのようなメトリクスが取得できますか？

`GET /metrics` で Prometheus 形式のメトリクスを提供します。

- コマンド件数（`mygramdb_command_total`）。カウンターから毎秒の処理件数を計算可能
- テーブルごとのインデックスのドキュメント数と語数
- キャッシュヒット率、メモリ、エビクション件数
- プロセス RSS と集計されたインデックスメモリ
- レプリケーション状態、処理イベント数、最終適用イベントからの経過秒数
- 接続中のクライアント数と拒否リクエスト件数

### 「単一バイナリ」と言いつつ MySQL が必要 — それは本当にシンプルですか？

MygramDB は「既存の MySQL に検索レプリカを追加する」作業を小さくする設計です。データベースを置き換えるのではなく、MySQL の横に配置し、GTID/binlog 設定、レプリケーションユーザー、対象テーブル、ネットワーク許可範囲を設定します。スキーマ変更や検索用 ETL パイプラインは基本的に不要ですが、検索リクエストの向き先は MygramDB の TCP API または HTTP API へ切り替える必要があります。

## ベンチマーク

### ベンチマークのハードウェア環境は？

110万件の Wikipedia 記事（英語 100万件と日本語 10万件）でテストしました。MySQL 8.4.11 は Docker で実行し、MygramDB は `verify_text: all`（正規化文字列との部分文字列照合）、クエリキャッシュ無効で実行しています。Apple M5 Max ホスト（18 コア / 128 GiB）で Docker Desktop に 32 GiB を割り当て、コンテナからは 31.29 GiB が利用可能な状態で実行しました。各クエリはウォームアップ 5回のあと 200回計測しています。計測したクエリの件数は MySQL FULLTEXT と同じでしたが、すべてのクエリで同じ意味になることを示すものではありません。別のハードウェアやメモリ上限では絶対レイテンシが変わります。

### ベンチマークで MySQL 側の設定はチューニングしましたか？

しています。`innodb_buffer_pool_size` を 8.0 GiB に設定し、FULLTEXT の作業セットが収まる状態で計測しました。実行中のバッファプールヒット率は 99.9989%、ディスク読み込みは 7,809回です。[ベンチマーク](/ja/benchmarks)の数値は、十分なメモリを与えたウォーム状態の FULLTEXT との比較です。

### MySQL はコールドキャッシュとウォームキャッシュのどちらでテストしましたか？

ウォームです。実行中のバッファプールヒット率が 99.9989% なので、MySQL FULLTEXT はほぼメモリから読んでいます。同じ計測で MygramDB 側のクエリキャッシュは無効にしているため、MygramDB の数値はキャッシュヒットではなく検索エンジンの実処理を表します。どちらの設定も[ベンチマーク](/ja/benchmarks)に記載しています。

### なぜ Elasticsearch との実測比較がないのですか？

Elasticsearch の性能はクラスタ構成、シャード設計、マッピング、JVM 設定で大きく変わります。単純なシングルノード比較では用途差を説明しにくいため、このサイトでは[比較ページ](/ja/comparison)で定性的な使い分けを示しています。

## プロジェクト

### なぜ Rust ではなく C++ですか？

C++ を使うことで、ポスティングリスト、ビットマップ演算、DocID のデルタエンコーディングのメモリ配置を直接制御でき、MySQL C API と CRoaring も利用できます。リソース管理には RAII と `unique_ptr`、エラー処理には `Expected<T, Error>` を使っています。これは MygramDB の実装上の選択であり、適切な言語はプロジェクトの要件と利用するライブラリによって異なります。

### プロジェクトの成熟度は？

開発は 2025年 11月に開始しました。高トラフィックなサービスで本番利用実績があります（詳細は NDA により非公開）。

### MySQL FULLTEXT から MygramDB への移行方法は？

MySQL はそのまま維持し、MygramDB を横に立てて、検索クエリだけルーティングします。既存行は初回 `SYNC` で読み込み、その後の変更は binlog で追従します。[クイックスタート](/ja/)または[比較 — 移行方法](/ja/comparison#移行方法)をご覧ください。
